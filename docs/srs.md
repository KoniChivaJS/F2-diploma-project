# Специфікація вимог до програмного забезпечення (SRS)

**Система:** платформа гарантованої доставки вебхуків з підтримкою ізольованих логічних середовищ клієнтів
**Стандарт:** ISO/IEC/IEEE 29148:2018
**Версія:** 1.0 (після технічного аудиту) · **Джерело:** ЛР№4, підрозділ 1.5 (модель To-Be)

## 1. Вступ

### 1.1. Призначення

Документ визначає функціональні та нефункціональні вимоги, обмеження проєктування та критерії верифікації платформи гарантованої доставки вебхуків. Документ є вхідними даними для проєктування архітектури (C4 Model, ADR) і для методики експериментального дослідження стійкості до навантаження.

### 1.2. Обсяг (Scope)

У межах системи:

- прийом подій від систем-постачальників через HTTP API;
- довговічне збереження подій і публікація їх у брокер повідомлень;
- маршрутизація подій за підписками;
- доставка підписаних HTTP-запитів на endpoint-и отримувачів із повторними спробами;
- керування середовищами клієнтів, endpoint-ами, підписками, типами подій і секретами;
- спостережуваність доставки;
- експериментальний стенд для дослідження стійкості до навантаження.

Поза межами системи: бізнес-логіка систем-постачальників, обробка подій на стороні отримувачів, білінг, автентифікація машина–машина за OAuth 2.0 Client Credentials (замість неї застосовуються API-ключі за SRS-NFR-SEC-01).

### 1.3. Скорочена форма терміна

«Середовище клієнта» — визначена скорочена форма терміна «ізольоване логічне середовище клієнта (tenant)» (див. розділ 11).

## 2. Контекст системи (System Context)

### 2.1. Перспектива продукту

Система є модульним монолітом із п'ятьма обмеженими контекстами (Ingestion, Routing, Delivery, Tenancy, Observability), які розгортаються як окремо масштабовані процеси однієї кодової бази: API прийому та керування, ретранслятор outbox, delivery-воркери, планувальник фонових завдань (Kubernetes CronJob), портал адміністрування (Next.js у режимі BFF). DLQ завдань доставки зберігається в СУБД; DLQ poison-повідомлень — окрема тема (черга) брокера.

### 2.2. Зовнішні сутності та інтерфейси

| Сутність | Роль | Інтерфейс |
|---|---|---|
| Система-постачальник подій | Надсилає події | REST API `/v1/events`, HTTPS, API-ключ |
| Адміністратор середовища клієнта | Керує endpoint-ами, підписками, секретами | Портал (HTTPS, OIDC) і REST API керування |
| Оператор платформи | Керує середовищами клієнтів, запускає експерименти | REST API керування, kubectl, Terraform |
| Отримувач (endpoint) | Приймає підписані запити | HTTP(S) POST за Standard Webhooks |
| SMTP-сервіс | Доставляє сповіщення | SMTP / TLS |
| Провайдер ключів, сумісний із KMS | Зберігає KEK | HTTPS API (на стенді — OpenBao Transit) |
| Провайдер ідентичності | Автентифікація користувачів порталу | OIDC (на стенді — Keycloak) |

### 2.3. Ролі користувачів (RBAC)

| Роль | Права |
|---|---|
| `producer` (API-ключ) | Публікація подій у межах свого середовища клієнта |
| `env_admin` | Керування endpoint-ами, підписками, секретами, типами подій, DLQ свого середовища клієнта |
| `env_viewer` | Перегляд журналу спроб і метрик свого середовища клієнта |
| `platform_operator` (API-ключ, доступ лише через внутрішній Service) | Керування середовищами клієнтів і квотами, запуск експериментальних прогонів |

### 2.4. Обмеження

- Проєкт виконує один розробник.
- Система розгортається в одному кластері Kubernetes без географічної реплікації.
- Сховище резервних копій розміщується поза кластером на тому самому фізичному майданчику; залишковий ризик спільного домену відмови прийнято.

### 2.5. Припущення та залежності

- Годинники вузлів кластера синхронізовано через NTP з розходженням ≤ 10 мс (від цього залежать SRS-NFR-SEC-04 і SRS-NFR-PERF-02).
- Отримувачі підтримують TLS ≥ 1.2.

## 5. Нефункціональні вимоги (Non-Functional Requirements)

### 5.0. Профіль навантаження і бюджет ресурсів

**Профіль ПН-1 (номінальний):** 500 запитів/с, виконавець k6 `constant-arrival-rate` (відкрита модель); payload 1 КБ; 10 середовищ клієнтів із рівномірним розподілом; 1 підписка на подію; заглушка отримувача з фіксованою затримкою 50 мс і відповіддю 204; прогрів 60 с (виключається з вибірки); вимірювання 10 хв; 3 повтори.

### 8.2. Інваріант збереженості подій

Для кожного `event_id`, на який повернуто 202, і кожного `endpoint_id` з множини його підписок існує щонайменше один запит, отриманий заглушкою отримувача (за `webhook-id`), або запис у DLQ. Перевірку виконує SQL-скрипт звірки після прогону. Частка дублікатів вимірюється окремо і не є критерієм відмови.

export const options = {

  thresholds: {
    'http_req_duration{scenario:ingest}': ['p(95)<100', 'p(99)<250'],
    'http_req_failed{scenario:ingest}': ['rate<0.001'],
    'dropped_iterations': ['count<1'],
  },
};

## 11. Глосарій (Glossary)

| Термін | Визначення |
|---|---|
| Вебхук (webhook) | HTTP-запит, який платформа надсилає на зареєстровану URL-адресу отримувача за подією, прийнятою від системи-постачальника. |
| Ізольоване логічне середовище клієнта (tenant); скорочено — середовище клієнта | Логічний розділ платформи з власними endpoint-ами, підписками, секретами, типами подій і квотами. |
| Endpoint | Зареєстрована URL-адреса отримувача з параметрами доставки (тайм-аут, ліміт Bulkhead, `ordered`). |
| Підписка | Правило, що зв'язує тип події та вираз фільтра з endpoint-ом. |
| Завдання доставки | Пара (подія, endpoint), що доставляється незалежно від інших пар. |
| At-least-once | Семантика доставки, за якої кожне завдання доставки доставляється щонайменше один раз; допускаються дублікати. |
| Idempotency key | Ключ запиту прийому; повторний запит із тим самим ключем не створює нової події. |
| Transactional Outbox | Патерн, за якого подія записується до таблиці outbox у тій самій транзакції, що й зміна стану, а публікацію в брокер виконує окремий ретранслятор. |
| Dead Letter Queue (DLQ) | Сховище завдань доставки, для яких вичерпано ліміт спроб або отримано постійну відмову. |
| Replay | Повторне надсилання завдання з DLQ зі збереженням `webhook-id`. |
| Full jitter | Стратегія затримки повтору `random(0, min(cap, base·2^(n−1)))`. |
| Circuit Breaker | Механізм, що тимчасово припиняє запити до endpoint-а з високою часткою відмов (стани Closed, Open, Half-Open). |
| Bulkhead | Обмеження кількості одночасних запитів до одного endpoint-а, що ізолює його від спільного пулу воркерів. |
| Token Bucket | Алгоритм обмеження частоти з параметрами швидкості поповнення R і розміру сплеску B. |
| Deficit Round Robin (DRR) | Алгоритм справедливого планування, що розподіляє слоти між чергами пропорційно вагам із квантом Q. |
| Envelope encryption | Схема шифрування, за якої дані шифруються ключем DEK, а DEK — ключем KEK у провайдері ключів. |
| Consumer lag | Кількість повідомлень брокера, ще не оброблених групою споживачів. |
| RPO / RTO | Допустимий обсяг втрачених даних / допустимий час відновлення після відмови. |
| Latency p95 | 95-й процентиль вибірки затримок за вікно вимірювання профілю навантаження без інтервалу прогріву. |
