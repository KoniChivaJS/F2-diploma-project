# Звіт Code Review діаграм C4 (рівні 1–2)

**Об'єкт перевірки:** `c4/l1_v1.mmd` (C4Context), `c4/l2_v1.mmd` (C4Container)
**Еталон:** SRS платформи гарантованої доставки вебхуків, версія 1.0 (ISO/IEC/IEEE 29148:2018)
**Критерії:** 1 — відповідність SRS і трасування; 2 — логіка контейнерів рівня 2; 3 — зв'язки та протоколи; 4 — відмовостійкість і безпека
**Дата:** 2026-11-18

## 0. Умови перевірки

### 0.1. Шкала критичності

| Позначка | Рівень | Критерій |
|---|---|---|
| К | Критично | Діаграма суперечить вимозі Must або приховує нерозв'язане архітектурне рішення, від якого залежить виконання вимог Must |
| В | Високо | Відсутній елемент або зв'язок, необхідний для трасування вимоги Must; відсутній протокол на зв'язку |
| С | Середньо | Неповний або неоднозначний опис; відсутнє трасування вимоги Should; порушення нотації C4 |
| Н | Низько | Оформлення, термінологія, узгодженість підписів |

### 0.2. Обмеження, враховані в рекомендаціях

- Проєкт виконує один розробник (SRS 2.4).
- Один кластер Kubernetes без географічної реплікації; сховище резервних копій — поза кластером на тому самому майданчику (SRS 2.4).
- Рекомендації обмежено інструментами стека SRS-DC-01…09 і розділів 4, 8. Свідомо не запропоновано: OWASP ZAP, Chaos Mesh, Kyverno, HashiCorp Vault (виключені рішеннями за аудитом SRS), а також окремий продукт API Gateway, service mesh і вихідний проксі (обґрунтування — R4-01, R4-10).

### 0.3. Формат зауваження

Кожне зауваження містить: **Фрагмент** (елемент або стрілку діаграми), **Підстава** (пункт SRS або правило нотації C4), **Проблема**, **Виправлення**. Фрагменти коду Mermaid наведено як вставки до наявних діаграм, а не як самостійні діаграми.

### R1-01 · С · Тип елемента «Система-постачальник подій»

- **Фрагмент:** L1 і L2 — `Person(producer, "Система-постачальник подій", ...)`.
- **Підстава:** SRS 2.2 — сутність є програмною системою з інтерфейсом REST API та API-ключем (роль `producer`, SRS 2.3); нотація C4 — програмна система, що є ініціатором взаємодії, позначається як зовнішня система, а не особа.
- **Проблема:** елемент `Person` позначає людину. Машинний клієнт з API-ключем відображено як людину; на рівні 2 це створює хибне уявлення про інтерактивний доступ.
- **Виправлення:**

```
System_Ext(producer, "Система-постачальник подій", "Сервіс клієнта; публікує доменні події з API-ключем (роль producer)")
```

### R1-02 · С · Відсутня роль `env_viewer`

- **Фрагмент:** L1, L2 — набір елементів `Person`.
- **Підстава:** SRS 2.3 — роль `env_viewer`: перегляд журналу спроб і метрик свого середовища клієнта; SRS-FUN-07.2.
- **Проблема:** на діаграмах представлено 3 з 4 ролей RBAC. Функція перегляду журналу спроб не має актора.
- **Виправлення:** додати окремий елемент або узагальнити роль у межах одного елемента з переліком ролей.

```
Person(envUser, "Користувач середовища клієнта", "Ролі env_admin (керування) і env_viewer (перегляд журналу спроб і метрик)")
```

### R1-03 · В · Відсутній експериментальний стенд

- **Фрагмент:** L1, L2 — повністю.
- **Підстава:** SRS 1.2 (стенд — у межах системи), SRS-EXP-01…04, SRS 5.0 (k6 на окремому вузлі поза бюджетом), SRS-NFR-PERF-01 (k6 звертається через Service без Ingress), SRS-NFR-REL-02, REL-03 (токсики Toxiproxy), SRS 8.2 (SQL-скрипт звірки).
- **Проблема:** складова обсягу системи не відображена на жодному рівні. Зв'язок оператора «запускає експерименти» (опис `operator` на L1) не має цільового елемента. На стенді змінюється топологія зв'язків (API → Toxiproxy → СУБД/брокер; воркер → Toxiproxy → заглушка отримувача), яку основна діаграма L2 не відображає.
- **Виправлення:** на L1 — окрема система «Експериментальний стенд»; на рівні 2 — окрема діаграма конфігурації стенда (рекомендовано) або окремий `System_Boundary` на наявній L2.

```
%% L1
System(stand, "Експериментальний стенд", "k6, Toxiproxy, заглушка отримувача, звірка інваріанта 8.2")
Rel(operator, stand, "Запускає прогони за матрицею SRS-EXP-01", "kubectl / HTTPS (Kubernetes API)")
Rel(stand, platform, "Генерує навантаження ПН-1, вносить мережеві відмови", "HTTP (Service, без Ingress); TCP-проксі")

%% L2-стенд
System_Boundary(sb, "Експериментальний стенд") {
  Container(k6, "Генератор навантаження", "k6", "constant-arrival-rate 500 запитів/с; окремий вузол поза бюджетом 5.0")
  Container(toxi, "Toxiproxy", "Toxiproxy", "Затримка, тайм-аут, розрив з'єднання (SRS-EXP-04)")
  Container(stub, "Заглушка отримувача", "WireMock", "Затримка 50 мс, відповідь 204; фіксація webhook-id")
  Container(recon, "Звірка інваріанта", "SQL-скрипт, Kubernetes Job", "Перевірка 8.2 після прогону")
}
Rel(k6, api, "POST /v1/events", "HTTP, Service ClusterIP")
Rel(worker, toxi, "Доставляє вебхук", "HTTP через TCP-проксі")
Rel(toxi, stub, "Проксіює", "TCP")
```

### R1-04 · В · Відсутнє сховище резервних копій

- **Фрагмент:** L1 — зовнішні системи.
- **Підстава:** SRS 2.4, SRS-NFR-REL-04 (б), SRS-NFR-REL-08 (S3-сумісне сховище поза кластером), SRS-NFR-SEC-08 (строк зберігання копій ≤ 30 діб).
- **Проблема:** зовнішня залежність, через яку виконуються RPO ≤ 60 с і PITR, на діаграмі контексту відсутня. Межа кластера і спільний домен відмови не задокументовані.
- **Виправлення:** див. також R4-03 (контейнери і зв'язки рівня 2).

```
SystemDb_Ext(backup, "S3-сумісне сховище резервних копій", "Поза кластером, той самий майданчик; 14 діб (REL-08); payload ≤ 30 діб (SEC-08)")
Rel(platform, backup, "Архівує WAL і повні копії СУБД", "HTTPS, S3 API")
```

### R1-05 · В · Відсутній контекст Observability

- **Фрагмент:** L1, L2 — повністю.
- **Підстава:** SRS 2.1 (обмежений контекст Observability), SRS-FUN-07.3–07.5, SRS-DC-08 (OpenTelemetry, Prometheus, Grafana, Jaeger), SRS-NFR-OBS-01 (Alertmanager), SRS 7.2 (каталог метрик).
- **Проблема:** один із п'яти обмежених контекстів і весь стек спостережуваності не відображені. Вимоги FUN-07.3, 07.4, 07.5 і OBS-01 не мають елемента-носія. Канал алертів до оператора відсутній.
- **Виправлення:** контейнери і зв'язки — у R4-06. На L1 — зв'язок алертів до оператора:

```
Rel(platform, operator, "Надсилає алерти OBS-01", "SMTP + STARTTLS")
```

### R1-06 · В · Фонові функції без контейнера-виконавця

- **Фрагмент:** L2 — описи `api`, `relay`, `worker`.
- **Підстава:** SRS-FUN-06.3 (вимкнення endpoint-а за 72 год), SRS-FUN-06.4 (e-mail ≤ 5 хв), SRS-NFR-REL-15 (повтори сповіщення до 24 год), SRS-NFR-SEC-08 (видалення payload > 30 діб), SRS-NFR-SEC-09 (виконання запиту на стирання), SRS-NFR-REL-12 (видалення опублікованих записів outbox ≤ 24 год), SRS-NFR-REL-10 (відновлення розкладу в Redis ≤ 60 с).
- **Проблема:** сім функцій виконуються за розкладом, а не за запитом. Жоден контейнер L2 не містить їх в описі. `api` обробляє лише запити і не може бути носієм періодичних функцій без механізму обрання лідера.
- **Виправлення:** розподілити функції явно. Варіант із мінімальною складністю для одного розробника — окремий контейнер з того самого образу як Kubernetes CronJob (обрання лідера не потрібне); потребує оновлення SRS 2.1 (п'ятий процес).

| Функція | Вимога | Рекомендований виконавець |
|---|---|---|
| Вимкнення endpoint-а, e-mail, повтори сповіщення | FUN-06.3, 06.4, REL-15 | Планувальник (CronJob, інтервал ≤ 1 хв для 5-хвилинного строку FUN-06.4) |
| Видалення payload > 30 діб; виконання стирання | SEC-08, SEC-09 | Планувальник (CronJob, щодоби) |
| Видалення опублікованих записів outbox | REL-12 | `relay` |
| Відновлення розкладу в Redis | REL-10 | `worker` (під час старту і за виявлення втрати індексу) |

```
Container(scheduler, "Планувальник фонових завдань", "TypeScript, NestJS; Kubernetes CronJob", "Вимкнення endpoint-ів (FUN-06.3), сповіщення (FUN-06.4, REL-15), строк зберігання і стирання (SEC-08, SEC-09)")
Rel(scheduler, db, "Читає статистику спроб, видаляє прострочені дані", "TCP, протокол СУБД, TLS")
Rel(scheduler, smtp, "Надсилає сповіщення адміністраторам", "SMTP + STARTTLS")
```

### R1-07 · В · DLQ і replay не трасуються

- **Фрагмент:** L2 — описи `db`, `broker`, `worker`; зв'язки `api`.
- **Підстава:** SRS-FUN-03.5 (DLQ завдань), SRS-FUN-13 (окрема DLQ poison-повідомлень), SRS-FUN-06.4 (завдання вимкненого endpoint-а — до DLQ), SRS-FUN-03.6 (replay `POST /v1/dlq/{task_id}/replay`), SRS-NFR-SEC-08, SEC-09 (строк зберігання і стирання в DLQ), метрика `dlq_depth` (7.2).
- **Проблема:** на діаграмі не визначено місце зберігання двох різних DLQ. Від цього залежать: виконання стирання за `event_id` у DLQ (SEC-09), replay за `task_id`, джерело метрики `dlq_depth`. Шлях replay (API → стан завдання → розклад) відсутній.
- **Виправлення:** зафіксувати в ADR і в описах контейнерів: DLQ завдань — таблиця СУБД (стирання і replay виконуються запитами СУБД); DLQ poison-повідомлень — окрема тема/черга брокера з `retention.ms` ≤ 2 592 000 000.

```
ContainerDb(db, "СУБД", "...", "Події, outbox, конфігурація, стан завдань і розклад (джерело істини), спроби, DLQ завдань, журнал аудиту")
ContainerQueue(broker, "Брокер повідомлень", "...", "Теми events, tasks; тема poison-DLQ (FUN-13)")
Rel(worker, db, "Переносить завдання до DLQ (FUN-03.5, 06.4)", "TCP, протокол СУБД, TLS")
Rel(api, db, "Replay: повертає завдання з DLQ у стан очікування (FUN-03.6)", "TCP, протокол СУБД, TLS")
```

### R1-08 · С · Неповний опис контейнера `api`

- **Фрагмент:** L2 — `Container(api, "API", "NestJS", "Прийом подій і керування конфігурацією")`.
- **Підстава:** SRS-FUN-01.2, 01.3 (реєстр JSON Schema), 01.4–01.5 (ідемпотентність), SRS-FUN-09 (API-ключі), SRS-FUN-11 (типи подій), SRS-FUN-12 (життєвий цикл середовища клієнта і квоти), SRS-NFR-SEC-10 (журнал аудиту), SRS-NFR-SEC-19 (API стирання).
- **Проблема:** опис не дає змоги трасувати функції Tenancy та Ingestion до контейнера. Функції стирання (GDPR ст. 17) і аудиту не відображені на жодній діаграмі.
- **Виправлення:**

```
Container(api, "API прийому та керування", "TypeScript, NestJS (Node.js)", "Прийом і валідація подій (JSON Schema), ідемпотентність, Token Bucket; керування середовищами клієнтів, endpoint-ами, підписками, типами подій, секретами, API-ключами, DLQ/replay, стиранням; журнал аудиту")
```

### R1-09 · С · Неповний опис контейнера `portal`

- **Фрагмент:** L2 — `Container(portal, ..., "Інтерфейс керування endpoint-ами і підписками")`.
- **Підстава:** SRS 2.3 (`env_admin`: endpoint-и, підписки, секрети, типи подій, DLQ; `env_viewer`: журнал спроб, метрики), SRS-FUN-06.1, SRS-NFR-SEC-19 (API стирання доступний адміністратору середовища клієнта).
- **Проблема:** опис охоплює 2 з 7 функцій ролей порталу.
- **Виправлення:**

```
Container(portal, "Портал адміністрування", "TypeScript, Next.js", "Керування endpoint-ами, підписками, секретами, типами подій, DLQ і стиранням; перегляд журналу спроб і метрик середовища клієнта; усі дії — через API керування (FUN-06.1)")
```

### R1-10 · С · Джерело метрик для `env_viewer` не визначено

- **Фрагмент:** L2 — відсутній зв'язок для перегляду метрик середовища клієнта.
- **Підстава:** SRS 2.3 (`env_viewer` — метрики свого середовища клієнта), SRS-NFR-SEC-11 (ізоляція даних середовища клієнта), SRS-FUN-07.3 (мітки без необмеженої кардинальності).
- **Проблема:** прямий доступ користувачів середовища клієнта до Grafana/Prometheus порушує SEC-11: Prometheus не фільтрує ряди за обліковими даними. Діаграма не фіксує, що метрики для порталу формуються API з агрегатів СУБД.
- **Виправлення:** зафіксувати на L2 і в ADR: метрики середовища клієнта надає API (агрегати таблиці спроб з фільтром за середовищем клієнта); Grafana доступна лише оператору платформи.

```
Rel(portal, api, "Читає журнал спроб і агрегати метрик середовища клієнта (FUN-07.2)", "HTTPS, JSON; Bearer JWT")
```

### R1-11 · С · Інтерфейси і автентифікація оператора не визначені

- **Фрагмент:** L1 — `Rel(operator, platform, "Адмініструє")`; L2 — `Rel(operator, api, ...)`.
- **Підстава:** SRS 2.2 (оператор: REST API керування, kubectl, Terraform), SRS 2.3 (`platform_operator`), SRS-NFR-SEC-01, SEC-12.
- **Проблема:** SRS не визначає спосіб автентифікації оператора (API-ключ із областю дії `platform_operator` або OIDC через провайдер ідентичності). kubectl і Terraform взаємодіють з Kubernetes API, а не з платформою, і належать діаграмі розгортання, а не L1.
- **Виправлення:** додати до SRS 2.2 спосіб автентифікації оператора (відкрите питання до SRS); на L1 залишити зв'язок до API керування; kubectl/Terraform перенести на діаграму розгортання (R4-12).

```
Rel(operator, platform, "Керує середовищами клієнтів і квотами (FUN-12)", "HTTPS, REST API керування; Bearer JWT (OIDC)")
```

### R1-12 · Н · Найменування елементів не узгоджене з SRS

- **Фрагмент:** L1 — `System(platform, "Webhook Delivery Platform", ...)`, `System_Ext(idp, "Keycloak", ...)`, `System_Ext(kms, "Провайдер ключів (KMS)", ...)`.
- **Підстава:** SRS (найменування системи), SRS 2.2 («Провайдер ідентичності (на стенді — Keycloak)», «Провайдер ключів, сумісний із KMS (на стенді — OpenBao Transit)»).
- **Проблема:** назва системи англійською не збігається з найменуванням SRS. Зовнішня система `idp` названа продуктом, а не роллю; для `kms` реалізацію на стенді не вказано.
- **Виправлення:**

```
System(platform, "Платформа гарантованої доставки вебхуків", "...")
System_Ext(idp, "Провайдер ідентичності", "OIDC; на стенді — Keycloak")
System_Ext(kms, "Провайдер ключів, сумісний із KMS", "Зберігання KEK; на стенді — OpenBao Transit")
```

## 2. Аналіз архітектурної логіки контейнерів (рівень 2)

Перелік контейнерів `api`, `relay`, `worker`, `portal` збігається з чотирма процесами SRS 2.1. Підміни контейнерів класами або компонентами в наборі елементів не виявлено. Зауваження нижче стосуються технологічної відповідності, розподілу стану між репліками та описів.

### R2-01 · К · Сховище і брокер задано однією технологією

- **Фрагмент:** `ContainerDb(db, "PostgreSQL", "SQL", ...)`, `ContainerQueue(broker, "Kafka", "Брокер", ...)`.
- **Підстава:** SRS-DC-04 (PostgreSQL, MySQL, MongoDB через спільний порт репозиторію; Kafka, RabbitMQ через спільний порт брокера), SRS-EXP-01 (домен параметрів СУБД і брокера), SRS-NFR-MNT-01 (паритет адаптерів), SRS-RQ-02.
- **Проблема:** об'єкт експериментального дослідження — порівняння конфігурацій СУБД і брокерів. Діаграма фіксує одну конфігурацію і не відображає змінну архітектури. Опис `PostgreSQL` як назви контейнера суперечить портам DC-04.
- **Виправлення:** назвати контейнери за роллю, технології подати як варіанти, базову конфігурацію позначити окремо. Розподіл на порти й адаптери показати на рівні 3 (Component).

```
ContainerDb(db, "СУБД", "PostgreSQL 16+ (базова) | MySQL 8 | MongoDB (replica set)", "Через порт репозиторію (DC-04); вибір — параметр прогону EXP-01")
ContainerQueue(broker, "Брокер повідомлень", "Apache Kafka (базова) | RabbitMQ", "Через порт брокера (DC-04); вибір — параметр прогону EXP-01")
```

Версії в полі технології фіксуються за фактичними образами Helm-чартів; наведені значення — шаблон.

### R2-02 · К · Не визначено розподіл стану endpoint-а між репліками воркерів

- **Фрагмент:** `Container(worker, ...)`, `Rel(worker, broker, "Споживає завдання")`, `Rel(worker, redis, "Планує повтори")`.
- **Підстава:** SRS-FUN-04.1 (Bulkhead на endpoint; завдання понад ліміт не займають слоти інших endpoint-ів), SRS-FUN-04.2–04.4 (Circuit Breaker за останніми 20 спробами endpoint-а), SRS-FUN-02.5 (`ordered = true`), SRS-FUN-05.2 (ліміт частоти на endpoint), SRS-FUN-05.3 (DRR між середовищами клієнтів), SRS-NFR-REL-02, SRS-EXP-01 (репліки воркерів ∈ {1, 3, 5}), SRS-NFR-PERF-06 (12 партицій, до 12 реплік).
- **Проблема:** за кількості реплік > 1 стан Bulkhead, Circuit Breaker і порядку на endpoint або локальний (тоді всі завдання endpoint-а мають потрапляти до однієї репліки), або спільний (Redis). Діаграма не фіксує жоден варіант. Наслідки, не відображені на схемі:
  1. Ключ партиції Kafka `endpoint_id` забезпечує локальність стану і порядок, але створює блокування черги (head-of-line): завдання endpoint-а, що перевищив ліміт Bulkhead або має Circuit Breaker у стані Open, затримують завдання інших endpoint-ів тієї самої партиції. Це порушує FUN-04.1 і є прямим механізмом відмови REL-02.
  2. Ребалансування груп споживачів під час масштабування KEDA переносить партиції між репліками; локальний стан Circuit Breaker обнуляється.
  3. RabbitMQ не має спорідненості повідомлення до споживача за ключем без додаткової конфігурації (consistent hash exchange або single active consumer); адаптер брокера не забезпечує тих самих гарантій, що порушує паритет MNT-01 без документування відмінностей.
- **Виправлення:** оформити ADR «Розподіл стану endpoint-а між репліками воркерів» з рішеннями: (а) ключ партиції/маршрутизації завдань — `endpoint_id`; (б) завдання, що не можуть бути виконані негайно (ліміт Bulkhead, ліміт частоти, стан Open), виводяться з потоку партиції до розкладу (СУБД + індекс Redis) з підтвердженням зсуву, без збільшення лічильника спроб (FUN-04.4, 05.2); (в) поведінку адаптера RabbitMQ задокументовано за MNT-01. Відобразити рішення на зв'язках L2:

```
Rel(worker, broker, "Споживає завдання; ключ партиції endpoint_id", "Kafka protocol (TCP 9092, TLS) | AMQP 0-9-1 (TCP 5671, TLS)")
Rel(worker, redis, "Відкладає завдання понад ліміт Bulkhead / частоти / стану Open", "RESP (TCP 6379, TLS)")
```

### R2-03 · В · Опис Redis суперечить SRS-NFR-REL-10 і SRS-DC-06

- **Фрагмент:** `ContainerDb(redis, "Redis", "Key-Value", "Token Bucket, кеш, розклад повторів")`.
- **Підстава:** SRS-NFR-REL-10 (джерело істини стану завдання і часу наступної спроби — СУБД; Redis — похідний індекс), SRS-DC-06 (механізм відкладених повторів — Redis або персистентні retry-топіки — фіксується в ADR), SRS-NFR-PERF-07 (канал інвалідації кешу маршрутизації), SRS-FUN-05.4 (fail-open).
- **Проблема:** формулювання «розклад повторів» позначає Redis як носія розкладу. Рішення DC-06 зафіксоване на діаграмі без посилання на ADR. Функція «кеш» не конкретизована: кеш конфігурації маршрутизації (PERF-07) зберігається в пам'яті воркера, Redis виконує роль каналу інвалідації.
- **Виправлення:**

```
ContainerDb(redis, "Redis", "Redis 7, Lua-скрипти", "Token Bucket (DC-05); похідний індекс розкладу повторів — джерело істини в СУБД (REL-10, ADR за DC-06); канал інвалідації кешу маршрутизації (PERF-07)")
```

### R2-04 · С · Контейнер `worker` поєднує контексти Routing і Delivery без опису двох ролей

- **Фрагмент:** `Container(worker, "Delivery Worker", "NestJS", "Маршрутизація, доставка, повтори")`.
- **Підстава:** SRS 2.1 (процеси: API, ретранслятор, delivery-воркери, портал), SRS-FUN-02.3–02.4 (маршрутизація подій у завдання), SRS-NFR-PERF-06 (KEDA за consumer lag), опис `broker` («Теми подій і завдань доставки»).
- **Проблема:** SRS 2.1 не виділяє маршрутизацію в окремий процес, тому поєднання в одному контейнері відповідає SRS. Проте діаграма не показує, що контейнер є споживачем двох тем у різних групах споживачів і продюсером теми завдань. Ціль масштабування KEDA (lag якої теми) не визначена.
- **Виправлення:** залишити один контейнер; уточнити опис і зв'язки (див. R3-15). Альтернатива — окремий контейнер `router` з того самого образу; потребує оновлення SRS 2.1.

```
Container(worker, "Delivery Worker", "TypeScript, NestJS (Node.js)", "Модуль Routing: events → tasks (FUN-02.3, 02.4); модуль Delivery: tasks → HTTP-доставка, Bulkhead, Circuit Breaker, DRR, повтори; масштабування KEDA за lag теми tasks")
```

### R2-05 · С · Межа виконання коду порталу не визначена

- **Фрагмент:** `Container(portal, "Admin Portal", "Next.js", ...)`, `Rel(portal, api, ...)`, `Rel(portal, idp, ...)`.
- **Підстава:** SRS-NFR-SEC-12 (Authorization Code + PKCE; API перевіряє JWT); нотація C4 — код, що виконується в браузері, і сервер, що його віддає, є різними контейнерами.
- **Проблема:** PKCE застосовується для публічного клієнта, токен якого зберігається в браузері; тоді запити до API надходять із браузера, а не з серверного процесу Next.js. Якщо портал працює як BFF (серверна частина Next.js тримає токен і проксіює запити), зв'язки інші. Діаграма не фіксує жоден варіант, а напрям зв'язків `portal → api` і `portal → idp` залежить від вибору.
- **Виправлення:** обрати варіант у ADR. Для варіанта BFF (токен не потрапляє в браузер):

```
Container(portal, "Портал адміністрування", "TypeScript, Next.js (BFF, серверний рендеринг)", "Зберігає токени в серверному сеансі; проксіює виклики до API керування")
Rel(envAdmin, portal, "Керує конфігурацією середовища клієнта", "HTTPS (TLS 1.3), браузер")
Rel(portal, idp, "Обмінює код авторизації на токени (PKCE)", "HTTPS, OIDC")
Rel(portal, api, "Викликає API керування", "HTTPS, JSON; Bearer JWT")
```

### R2-06 · С · Поле технології не містить технологій

- **Фрагмент:** `"NestJS"` (`api`, `relay`, `worker`), `"Next.js"` (`portal`), `"SQL"` (`db`), `"Брокер"` (`broker`), `"Key-Value"` (`redis`).
- **Підстава:** нотація C4 — поле technology контейнера містить мову, фреймворк, середовище виконання; SRS-DC-01.
- **Проблема:** «SQL», «Key-Value», «Брокер» — категорії, а не технології; мова TypeScript і середовище Node.js відсутні.
- **Виправлення:** `"TypeScript, NestJS (Node.js)"`, `"TypeScript, Next.js"`; для сховищ — за R2-01, R2-03.

### R2-07 · Н · Прийом і керування в одному контейнері

- **Фрагмент:** `Container(api, "API", ...)`.
- **Підстава:** SRS 2.1 («API прийому та керування»), SRS-NFR-PERF-01 (латентність прийому), SRS 5.0 (бюджет прикладного рівня), SRS-NFR-SEC-18 (ліміт API керування 10 запитів/с).
- **Проблема:** поєднання відповідає SRS 2.1. Наслідок не задокументовано: навантаження API керування споживає бюджет 2 vCPU / 1 ГБ, що вимірюється PERF-01.
- **Виправлення:** зафіксувати в ADR: один образ, один контейнер; навантаження API керування під час прогонів ПН-1 відсутнє. Альтернатива — два Deployment одного образу з різними наборами маршрутів (тоді на L2 — два контейнери).

### R2-08 · С · Конкурентність ретранслятора outbox не визначена

- **Фрагмент:** `Container(relay, "Outbox Relay", ...)`, `Rel(relay, db, "Читає outbox", "SQL")`.
- **Підстава:** SRS-FUN-02.1 (пакети N, опитування ≤ 100 мс), SRS-NFR-REL-01 (відмова pod-а ретранслятора без втрат), SRS-NFR-REL-07 (PDB `minAvailable: 1` за кількості реплік ≥ 2), SRS-NFR-PERF-04.
- **Проблема:** кількість реплік ретранслятора і спосіб виключення подвійного вибору записів не визначені. За однієї репліки відмова pod-а зупиняє публікацію до перезапуску (зростання `outbox_relay_lag_seconds` понад 500 мс). За кількох реплік без блокування — дублікати публікацій.
- **Виправлення:** зафіксувати в ADR і в описі контейнера: ≥ 2 репліки; вибір пакета з блокуванням рядків (`SELECT … FOR UPDATE SKIP LOCKED` для PostgreSQL і MySQL 8; атомарне `findOneAndUpdate` з позначкою власника для MongoDB); дублікати допускаються семантикою at-least-once (FUN-10).

```
Container(relay, "Outbox Relay", "TypeScript, NestJS (Node.js)", "Polling publisher (DC-03); ≥ 2 репліки, SKIP LOCKED; видалення опублікованих записів ≤ 24 год (REL-12)")
```

### R2-09 · Н · Міграції схеми не відображено

- **Фрагмент:** L2 — відсутній короткоживучий контейнер міграцій.
- **Підстава:** SRS-DC-01 (Prisma), SRS-NFR-SEC-10 (роль застосунку без UPDATE/DELETE на таблицю аудиту), SRS-NFR-MNT-05 (розгортання з нуля).
- **Проблема:** права на DDL і на таблицю аудиту має окрема роль СУБД; процес, що її використовує, не відображено.
- **Виправлення:**

```
Container(migrate, "Міграції схеми", "Prisma Migrate; Kubernetes Job (Argo CD PreSync)", "Застосовує DDL з окремою роллю СУБД")
Rel(migrate, db, "Застосовує міграції", "TCP, протокол СУБД, TLS")
```

### R2-10 · Н · Оформлення діаграми L2

- **Фрагмент:** `Person(producer)`, `Person(envAdmin)`, `Person(operator)` без описів; відсутня конфігурація розкладки.
- **Підстава:** нотація C4 — кожна діаграма самодостатня; Mermaid C4 — `UpdateLayoutConfig`, `UpdateRelStyle`.
- **Проблема:** L2 без L1 не пояснює ролі акторів. За 15+ зв'язків підписи накладаються.
- **Виправлення:** перенести описи акторів з L1; додати:

```
UpdateLayoutConfig($c4ShapeInRow="3", $c4BoundaryInRow="1")
UpdateRelStyle(worker, receiver, $offsetY="-20")
```

### R3-01 · С · L1: producer → platform

- **Фрагмент:** `Rel(producer, platform, "Публікує події", "REST / HTTPS")`.
- **Підстава:** SRS 2.2 (`/v1/events`, HTTPS, API-ключ), SRS-NFR-SEC-02 (вхідні — лише TLS 1.3), SRS-NFR-SEC-01.
- **Проблема:** REST — архітектурний стиль, не протокол; версія TLS і спосіб автентифікації не вказані.
- **Виправлення:** `Rel(producer, platform, "Публікує події (POST /v1/events)", "HTTPS (TLS 1.3), JSON; API-ключ")`

### R3-02 · С · L1: envAdmin → platform

- **Фрагмент:** `Rel(envAdmin, platform, "Керує конфігурацією", "HTTPS")`.
- **Підстава:** SRS 2.2 (портал і REST API керування, OIDC), SRS 2.3.
- **Проблема:** підпис «Керує конфігурацією» не визначає об'єкт керування; спосіб автентифікації відсутній.
- **Виправлення:** `Rel(envUser, platform, "Керує endpoint-ами, підписками, секретами, DLQ; переглядає журнал спроб", "HTTPS (TLS 1.3), браузер; OIDC")`

### R3-03 · В · L1: operator → platform без технології

- **Фрагмент:** `Rel(operator, platform, "Адмініструє")`.
- **Підстава:** SRS 2.2 (REST API керування), SRS-FUN-12.
- **Проблема:** абстрактний підпис і відсутній протокол. Стрілка не трасується до жодної функціональної вимоги.
- **Виправлення:** див. R1-11: `Rel(operator, platform, "Керує середовищами клієнтів і квотами (FUN-12)", "HTTPS, REST API керування; Bearer JWT (OIDC)")`

### R3-04 · Н · L1: platform → receiver

- **Фрагмент:** `Rel(platform, receiver, "Надсилає підписані вебхуки", "HTTPS POST")`.
- **Підстава:** SRS 2.2 (Standard Webhooks), SRS-NFR-SEC-02 (вихідні TLS ≥ 1.2), SRS-NFR-SEC-04 (HMAC-SHA256).
- **Проблема:** не вказано схему підпису і мінімальну версію TLS.
- **Виправлення:** `Rel(platform, receiver, "Надсилає підписані вебхуки (Standard Webhooks, HMAC-SHA256)", "HTTPS POST (TLS ≥ 1.2)")`

### R3-05 · С · L1/L2: SMTP без TLS

- **Фрагмент:** L1 `Rel(platform, smtp, ..., "SMTP")`; L2 `Rel(api, smtp, ..., "SMTP")`.
- **Підстава:** SRS 2.2 («SMTP / TLS»), SRS-NFR-REL-13 (тайм-аут SMTP 10 с).
- **Проблема:** протокол без захисту каналу; суперечить SRS 2.2.
- **Виправлення:** технологія `"SMTP + STARTTLS (TCP 587)"` або `"SMTPS (TCP 465)"` — за налаштуваннями SMTP-сервісу.

### R3-06 · В · L1: відсутній зв'язок platform → idp

- **Фрагмент:** L1 — наявний лише `Rel(envAdmin, idp, "Автентифікується", "OIDC")`.
- **Підстава:** SRS-NFR-SEC-12 (API перевіряє JWT: `iss`, `aud`, `exp`, `nbf`; RS256/ES256).
- **Проблема:** для перевірки підпису JWT платформа отримує відкриті ключі провайдера ідентичності (JWKS). Залежність платформи від провайдера ідентичності на L1 відсутня. Підпис технології «OIDC» не вказує транспорт.
- **Виправлення:**

```
Rel(envUser, idp, "Автентифікується (Authorization Code + PKCE)", "HTTPS, OIDC")
Rel(platform, idp, "Отримує JWKS для перевірки JWT", "HTTPS")
```

### R3-07 · Н · L1: platform → kms

- **Фрагмент:** `Rel(platform, kms, "Розшифровує DEK", "HTTPS")`.
- **Підстава:** SRS-NFR-SEC-03 (envelope encryption; ротація KEK кожні 90 діб).
- **Проблема:** підпис охоплює лише розшифрування; операції генерації/шифрування DEK під час створення і ротації секрету не відображені.
- **Виправлення:** `Rel(platform, kms, "Генерує і шифрує DEK, розшифровує DEK (KEK не залишає провайдер)", "HTTPS, Transit API")`

### R3-08 · Н · L2: producer → api

- **Фрагмент:** `Rel(producer, api, "POST /v1/events", "REST / HTTPS")`.
- **Підстава:** SRS-FUN-01.1, 01.4, SRS-NFR-SEC-01, SEC-02.
- **Проблема:** підпис є маршрутом, а не дією; заголовок `Idempotency-Key`, TLS і автентифікація не вказані. Проміжний вхідний контейнер відсутній (R4-01).
- **Виправлення:** `Rel(producer, ingress, "Публікує подію (POST /v1/events, Idempotency-Key)", "HTTPS (TLS 1.3), JSON; API-ключ")`

### R3-09 · С · L2: envAdmin → portal

- **Фрагмент:** `Rel(envAdmin, portal, "Використовує", "HTTPS")`.
- **Підстава:** SRS 2.3.
- **Проблема:** підпис «Використовує» не несе інформації про функцію.
- **Виправлення:** `Rel(envUser, portal, "Керує конфігурацією і переглядає журнал спроб середовища клієнта", "HTTPS (TLS 1.3), браузер")`

### R3-10 · В · L2: portal → api без транспорту і автентифікації

- **Фрагмент:** `Rel(portal, api, "Викликає API керування", "REST")`.
- **Підстава:** SRS-FUN-06.1, SRS-NFR-SEC-12, SRS-NFR-SEC-02.
- **Проблема:** транспортний протокол відсутній; спосіб передачі облікових даних (Bearer JWT) не вказаний. Маршрут (через вхідний контейнер або всередині кластера) не визначений.
- **Виправлення:** `Rel(portal, api, "Викликає API керування", "HTTPS, JSON; Bearer JWT (RS256/ES256)")`

### R3-11 · С · L2: api → db

- **Фрагмент:** `Rel(api, db, "Записує події та outbox", "SQL")`.
- **Підстава:** SRS-FUN-01.4–01.7 (ідемпотентність, одна транзакція), SRS-NFR-SEC-10, SEC-11 (RLS), SRS-NFR-REL-11 (тайм-аут 2 с), SRS-DC-04.
- **Проблема:** «SQL» — мова запитів, не протокол; для MongoDB не застосовна. Підпис не відображає атомарність запису (ключова властивість Transactional Outbox) і операції читання конфігурації, ключів, схем, запису аудиту.
- **Виправлення:** `Rel(api, db, "В одній транзакції: подія + outbox + ключ ідемпотентності; CRUD конфігурації; журнал аудиту", "TCP, протокол СУБД (TLS); Prisma; тайм-аут 2 с")`

### R3-12 · В · L2: api → redis без технології

- **Фрагмент:** `Rel(api, redis, "Перевіряє квоти")`.
- **Підстава:** SRS-DC-05 (Token Bucket, Lua-скрипт), SRS-FUN-05.1, 05.4 (fail-open), SRS-NFR-PERF-07 (інвалідація кешу), SRS-NFR-REL-13 (тайм-аут Redis 200 мс).
- **Проблема:** протокол відсутній; публікація інвалідації кешу маршрутизації після зміни конфігурації не відображена; поведінка fail-open не відображена.
- **Виправлення:**

```
Rel(api, redis, "Token Bucket середовища клієнта (Lua, fail-open); публікує інвалідацію кешу маршрутизації", "RESP (TCP 6379, TLS); тайм-аут 200 мс")
```

### R3-13 · С · L2: relay → db

- **Фрагмент:** `Rel(relay, db, "Читає outbox", "SQL")`.
- **Підстава:** SRS-FUN-02.1, 02.2, SRS-NFR-REL-12.
- **Проблема:** ретранслятор також позначає записи опублікованими і видаляє їх; підпис «Читає» приховує операції запису. «SQL» — див. R3-11.
- **Виправлення:** `Rel(relay, db, "Вибирає пакет N (SKIP LOCKED), позначає опублікованим після підтвердження, видаляє через ≤ 24 год", "TCP, протокол СУБД (TLS)")`

### R3-14 · Н · L2: relay → broker

- **Фрагмент:** `Rel(relay, broker, "Публікує події", "Kafka protocol")`.
- **Підстава:** SRS-FUN-02.2, SRS-NFR-REL-05, SRS-DC-04.
- **Проблема:** не вказано гарантію підтвердження і захист каналу; варіант RabbitMQ відсутній.
- **Виправлення:** `Rel(relay, broker, "Публікує події в тему events (acks=all / publisher confirm)", "Kafka protocol (TCP, TLS), ідемпотентний продюсер | AMQP 0-9-1 (TLS)")`

### R3-15 · В · L2: worker → broker без технології; відсутній потік маршрутизації

- **Фрагмент:** `Rel(worker, broker, "Споживає завдання")`.
- **Підстава:** SRS-FUN-02.3, 02.4 (подія → завдання на кожну пару подія–endpoint), SRS-FUN-13 (poison-DLQ), SRS-NFR-REL-07 (повернення без підтвердження), опис `broker` («теми подій і завдань доставки»).
- **Проблема:** протокол відсутній. Шлях «тема events → маршрутизація → тема tasks» не відображено: на діаграмі немає споживача теми подій і продюсера теми завдань. Функції FUN-02.3, 02.4 і FUN-13 не трасуються до зв'язку.
- **Виправлення:**

```
Rel(worker, broker, "Routing: споживає events, публікує tasks (ключ endpoint_id), poison → DLQ-тема", "Kafka protocol (TCP, TLS) | AMQP 0-9-1 (TLS)")
Rel(worker, broker, "Delivery: споживає tasks; підтвердження зсуву після фіксації стану в СУБД", "Kafka protocol (TCP, TLS) | AMQP 0-9-1 (TLS)")
```

Якщо Mermaid розміщує дві стрілки між однією парою елементів із накладенням, підписи об'єднуються в одну стрілку або зміщуються `UpdateRelStyle`.

### R3-16 · С · L2: worker → db

- **Фрагмент:** `Rel(worker, db, "Зберігає спроби", "SQL")`.
- **Підстава:** SRS-NFR-REL-10 (стан завдання і час наступної спроби — у СУБД), SRS-FUN-07.1, SRS-FUN-03.5, SRS-FUN-02.3 (читання підписок), SRS-NFR-SEC-11.
- **Проблема:** підпис охоплює одну з чотирьох операцій: читання конфігурації маршрутизації, фіксацію стану завдання і розкладу (джерело істини), запис спроб, перенесення до DLQ.
- **Виправлення:** `Rel(worker, db, "Читає підписки й endpoint-и; фіксує стан завдання і час наступної спроби; записує спроби; переносить до DLQ", "TCP, протокол СУБД (TLS)")`

### R3-17 · В · L2: worker → redis без технології

- **Фрагмент:** `Rel(worker, redis, "Планує повтори")`.
- **Підстава:** SRS-FUN-05.2 (ліміт частоти на endpoint), SRS-NFR-REL-10, SRS-NFR-PERF-07 (підписка на інвалідацію), SRS-DC-06.
- **Проблема:** протокол відсутній; операції Token Bucket на endpoint і підписка на канал інвалідації не відображені; «планує» суперечить ролі похідного індексу (R2-03).
- **Виправлення:** `Rel(worker, redis, "Token Bucket endpoint-а; оновлює і читає похідний індекс розкладу; підписка на інвалідацію кешу", "RESP (TCP 6379, TLS); Pub/Sub")`

### R3-18 · Н · L2: worker → receiver

- **Фрагмент:** `Rel(worker, receiver, "Доставляє вебхук", "HTTPS")`.
- **Підстава:** SRS-FUN-03.1 (тайм-аут 1–30 с), SRS-FUN-03.2, SRS-NFR-SEC-02, SRS-NFR-SEC-05 (0 редиректів, фіксація IP).
- **Проблема:** параметри зв'язку, від яких залежить безпека (SSRF) і класифікація результату, не вказані.
- **Виправлення:** `Rel(worker, receiver, "Доставляє вебхук (webhook-id, webhook-timestamp, webhook-signature)", "HTTPS POST (TLS ≥ 1.2); тайм-аут 1–30 с; 0 редиректів; фіксація IP")`

### R3-19 · В · L2: відсутній зв'язок api → kms

- **Фрагмент:** L2 — наявний лише `Rel(worker, kms, "Розшифровує DEK", "HTTPS")`.
- **Підстава:** SRS-NFR-SEC-03 (envelope encryption), SRS-FUN-06.2 (ротація секрету підпису), SRS-DC-07.
- **Проблема:** створення і ротація секрету підпису виконуються API керування: генерація DEK і шифрування секрету потребують виклику провайдера ключів. Без цього зв'язку шлях SEC-03 на L2 неповний.
- **Виправлення:**

```
Rel(api, kms, "Генерує DEK і отримує його зашифровану форму під час створення / ротації секрету", "HTTPS, Transit API; тайм-аут 2 с")
Rel(worker, kms, "Розшифровує DEK; кеш у пам'яті ≤ 10 хв (REL-14)", "HTTPS, Transit API; тайм-аут 2 с")
```

### R3-20 · С · L2: api → smtp — невірне джерело зв'язку

- **Фрагмент:** `Rel(api, smtp, "Надсилає сповіщення", "SMTP")`.
- **Підстава:** SRS-FUN-06.3, 06.4 (сповіщення за результатами доставки за 72 год, строк ≤ 5 хв), SRS-NFR-REL-15 (повтори до 24 год).
- **Проблема:** подія, що ініціює сповіщення, виникає не в запиті до API, а в періодичній оцінці статистики спроб. API не є виконавцем цієї функції (R1-06).
- **Виправлення:** замінити джерело на контейнер-виконавець фонових функцій (R1-06): `Rel(scheduler, smtp, "Надсилає сповіщення про вимкнення endpoint-а; повтори до 24 год", "SMTP + STARTTLS (TCP 587); тайм-аут 10 с")`

### R3-21 · В · L2: розбіжність з L1 у зв'язках із провайдером ідентичності

- **Фрагмент:** L2 `Rel(portal, idp, "OIDC login", "HTTPS")`; відсутні `envAdmin → idp` (є на L1) і `api → idp`.
- **Підстава:** нотація C4 — зв'язки L1 декомпонуються на L2 без втрати; SRS-NFR-SEC-12.
- **Проблема:** зв'язок L1 `envAdmin → idp` на L2 втрачено і замінено зв'язком контейнера. Перевірка JWT в `api` (JWKS) не відображена на жодному рівні (див. R3-06).
- **Виправлення:**

```
Rel(envUser, idp, "Автентифікується (Authorization Code + PKCE)", "HTTPS, OIDC, браузер")
Rel(portal, idp, "Обмінює код на токени", "HTTPS, OIDC")
Rel(api, idp, "Отримує JWKS, кешує ключі", "HTTPS")
```

### R3-22 · Н · Змішування мов у підписах

- **Фрагмент:** `"OIDC login"`, `"Admin Portal"`, `"Outbox Relay"`, `"Delivery Worker"`, `"Webhook Delivery Platform"`.
- **Підстава:** узгодженість термінології з SRS (документ українською).
- **Проблема:** частина підписів англійською, частина українською.
- **Виправлення:** уніфікувати: назви контейнерів — за SRS 2.1 («Портал адміністрування», «Ретранслятор outbox», «Delivery-воркер»); дієслівні підписи зв'язків — українською.

## 4. Пропозиції щодо відмовостійкості та безпеки

### R4-01 · В · Відсутній вхідний контейнер (Ingress)

- **Фрагмент:** L2 — `producer`, `envAdmin`, `operator` звертаються до `api` і `portal` напряму.
- **Підстава:** SRS-NFR-SEC-02 (вхідні з'єднання — лише TLS 1.3), RTM SRS-NFR-SEC-02 («TLS-клієнт проти Ingress стенда»), SRS-NFR-PERF-01 (вимірювання через Service без Ingress), SRS-FUN-01.1 (обмеження тіла 256 КБ).
- **Проблема:** точка термінації TLS 1.3 відсутня; вимога SEC-02 не має елемента-носія. Діаграма не показує, що вимірювання PERF-01 виконується в обхід вхідного контейнера.
- **Виправлення:** додати контейнер Ingress-контролера (або контролера Gateway API); продукт обрати в ADR. Під час вибору врахувати, що проєкт ingress-nginx спільноти Kubernetes виведено з підтримки в 2026 р. (перевірити статус на дату вибору). Окремий продукт API Gateway не пропонується: автентифікація (SEC-01) і обмеження частоти (DC-05) реалізовані в `api`, дублювання цих функцій не потрібне.

```
Container(ingress, "Вхідний контролер", "Ingress / Gateway API controller (ADR)", "Термінація TLS 1.3; маршрутизація за хостом: ingest, керування, портал; ліміт тіла 256 КБ")
Rel(producer, ingress, "Публікує події", "HTTPS (TLS 1.3)")
Rel(envUser, ingress, "Звертається до порталу", "HTTPS (TLS 1.3)")
Rel(ingress, api, "Проксіює запити", "HTTP, Service ClusterIP")
Rel(ingress, portal, "Проксіює запити", "HTTP, Service ClusterIP")
```

### R4-02 · В · Брокер показано одним вузлом

- **Фрагмент:** `ContainerQueue(broker, "Kafka", ...)`.
- **Підстава:** SRS-NFR-REL-05 (Kafka: replication factor 3, `min.insync.replicas` = 2; RabbitMQ: quorum queues), SRS 5.0 («Kafka × 3»), SRS-NFR-REL-01 (відмова pod-а брокера без втрат).
- **Проблема:** RF = 3 і `min.insync.replicas` = 2 вимагають ≥ 3 брокерів; quorum queues RabbitMQ без 3 вузлів не витримують відмову вузла. Діаграма не фіксує кількість вузлів, від якої залежить виконання REL-01 і REL-05.
- **Виправлення:** вказати кількість вузлів в описі контейнера L2; топологію pod-ів — на діаграмі розгортання (R4-12).

```
ContainerQueue(broker, "Брокер повідомлень", "Apache Kafka, режим KRaft, 3 брокери | RabbitMQ, 3 вузли", "RF = 3, min.insync.replicas = 2; quorum queues; retention ≤ 30 діб (SEC-08)")
```

### R4-03 · В · Відсутній ланцюг резервного копіювання на L2

- **Фрагмент:** L2 — відсутні елементи pgBackRest і сховища копій.
- **Підстава:** SRS-NFR-REL-04 (б) (PITR, RPO ≤ 60 с, `archive_timeout = 60`, RTO ≤ 30 хв), SRS-NFR-REL-08, SRS 2.4.
- **Проблема:** вимога Must REL-08 для PostgreSQL не має елемента на L2. Межа кластера між СУБД і сховищем копій не показана.
- **Виправлення:**

```
Container(pgbackrest, "Резервне копіювання", "pgBackRest (sidecar / CronJob)", "WAL-архів (archive_timeout = 60), повні копії, PITR; 14 діб")
SystemDb_Ext(backup, "S3-сумісне сховище резервних копій", "Поза кластером, той самий майданчик")
Rel(pgbackrest, db, "Отримує WAL і дані", "TCP, протокол PostgreSQL / локальний том")
Rel(pgbackrest, backup, "Записує архів і копії", "HTTPS, S3 API")
```

Для MySQL (повна копія + binlog) і MongoDB (oplog-архівування) — аналогічні елементи на діаграмі конфігурації стенда з позначкою Should.

### R4-04 · С · Рішення щодо репліки СУБД не задокументовано

- **Фрагмент:** `ContainerDb(db, ...)` — один екземпляр.
- **Підстава:** SRS-NFR-REL-04 (а) (відмова pod-а з незмінним PV: RPO = 0, RTO ≤ 60 с), `synchronous_commit = on` (REL-01), SRS 2.4, SRS 5.0 (інфраструктурний рівень фіксований).
- **Проблема:** вимоги SRS виконуються одним екземпляром СУБД із перезапуском pod-а на тому самому PV; репліка СУБД не є вимогою. Відсутність репліки на діаграмі не супроводжується рішенням і залишковим ризиком (недоступність запису на час перезапуску, ≤ 60 с; втрата PV — сценарій PITR).
- **Виправлення:** репліку не додавати (додає компонент поза SRS і порушує порівнюваність прогонів для MySQL/MongoDB). Оформити ADR «Один екземпляр СУБД» з посиланням на REL-04 і REL-11 (503 із `Retry-After` на час перезапуску). Для MongoDB в описі зазначити replica set з одного вузла як умову транзакцій outbox.

### R4-05 · С · Відмовна поведінка Redis не відображена

- **Фрагмент:** `ContainerDb(redis, ...)`.
- **Підстава:** SRS-FUN-05.4 (fail-open з метрикою `ratelimit_backend_errors_total`), SRS-NFR-REL-10 (відновлення розкладу ≤ 60 с), SRS-NFR-PERF-07 (TTL ≤ 30 с за відмови каналу інвалідації).
- **Проблема:** один екземпляр Redis відповідає SRS, оскільки Redis є похідним сховищем. Діаграма не відображає поведінку інших контейнерів за його недоступності; виконавця відновлення розкладу не вказано (R1-06).
- **Виправлення:** доповнити опис: «один екземпляр без вимог до персистентності; за недоступності — fail-open обмеження частоти, TTL кешу 30 с, відновлення індексу розкладу з СУБД воркером ≤ 60 с». Репліку Redis не додавати.

### R4-06 · В · Відсутні контейнери спостережуваності

- **Фрагмент:** L2 — повністю.
- **Підстава:** SRS-DC-08, SRS-FUN-07.3, 07.4 (W3C Trace Context), 07.5 (дашборди з репозиторію), SRS-NFR-OBS-01, SRS-EXP-03 (знімок метрик Prometheus у звіті прогону).
- **Проблема:** метрики, трасування, дашборди й алерти, на яких побудовано верифікацію PERF-01…07, REL-01…03 і звіт EXP-03, не мають контейнерів.
- **Виправлення:** окремий `System_Boundary` «Стек спостережуваності» поза межею платформи. OpenTelemetry Collector входить до OpenTelemetry (DC-08) і відокремлює застосунок від бекендів; мінімальний варіант без Collector — експорт OTLP безпосередньо в Jaeger і збирання `/metrics` Prometheus (фіксується в ADR).

```
System_Boundary(obs, "Стек спостережуваності") {
  Container(otel, "OpenTelemetry Collector", "OpenTelemetry", "Приймає OTLP; експортує трасування і метрики")
  ContainerDb(prom, "Prometheus", "Prometheus", "Метрики каталогу 7.2; правила алертів")
  Container(am, "Alertmanager", "Prometheus Alertmanager", "Маршрутизація алертів OBS-01")
  ContainerDb(jaeger, "Jaeger", "Jaeger", "Трасування")
  Container(grafana, "Grafana", "Grafana", "Дашборди з JSON у репозиторії (FUN-07.5); доступ — лише оператор")
}
Rel(api, otel, "Трасування і метрики", "OTLP/gRPC (TCP 4317)")
Rel(relay, otel, "Трасування і метрики", "OTLP/gRPC (TCP 4317)")
Rel(worker, otel, "Трасування і метрики", "OTLP/gRPC (TCP 4317)")
Rel(otel, jaeger, "Експортує трасування", "OTLP/gRPC")
Rel(prom, otel, "Збирає метрики", "HTTP, /metrics")
Rel(prom, am, "Передає алерти", "HTTP")
Rel(am, smtp, "Надсилає алерти оператору", "SMTP + STARTTLS")
Rel(grafana, prom, "Запити PromQL", "HTTP")
Rel(grafana, jaeger, "Запити трасувань", "HTTP")
Rel(operator, grafana, "Переглядає дашборди", "HTTPS")
```

### R4-07 · С · Централізоване зберігання логів відсутнє у стеку

- **Фрагмент:** L2 — відсутній елемент логування.
- **Підстава:** SRS-NFR-SEC-13 (структуровані логи JSON із `trace_id`), SRS-NFR-SEC-19 (реєстрація інцидентів із часовими мітками для сповіщення за 72 год), SRS-DC-08 (стек без сховища логів).
- **Проблема:** SRS вимагає формату логів, але стек DC-08 не містить сховища логів; логи доступні лише в межах життя pod-а. Обмеження не задокументовано.
- **Виправлення:** нове сховище логів не додавати (поза стеком DC-08). Зафіксувати в ADR: логи — stdout контейнерів, доступ через Kubernetes API; кореляція — через `trace_id` у Jaeger; реєстрація інцидентів безпеки (SEC-19) — у журналі аудиту СУБД (SEC-10, строк ≥ 1 рік). На L2 відобразити журнал аудиту в описі `db`.

### R4-08 · С · Провайдер ідентичності в тому самому кластері

- **Фрагмент:** `System_Ext(idp, "Keycloak", ...)`.
- **Підстава:** SRS 2.2 («на стенді — Keycloak»), SRS 2.4 (один кластер), SRS-NFR-SEC-12 (access token ≤ 15 хв).
- **Проблема:** на стенді провайдер ідентичності розгортається в тому самому кластері, що й платформа, і має власну СУБД. Спільний домен відмови не позначено. Вплив недоступності провайдера ідентичності на платформу не визначено.
- **Виправлення:** в описі елемента зазначити «на стенді — у тому самому кластері, окремий namespace». Зафіксувати поведінку: прийом подій не залежить від провайдера ідентичності (API-ключі, SEC-01); API кешує JWKS і перевіряє вже видані токени без звернення до провайдера; за недоступності провайдера припиняється лише вхід у портал.

### R4-09 · С · Права доступу до провайдера ключів не розділено

- **Фрагмент:** `Rel(worker, kms, ...)`; відсутній `Rel(api, kms, ...)` (R3-19).
- **Підстава:** SRS-NFR-SEC-03, SRS-NFR-REL-14, SRS-DC-07.
- **Проблема:** діаграма не фіксує спосіб автентифікації контейнерів у провайдері ключів і розмежування операцій. Компрометація воркера з правом генерації ключів розширює вплив.
- **Виправлення:** зафіксувати в ADR і в підписах: автентифікація в OpenBao — метод Kubernetes auth (токен ServiceAccount); політика `api` — лише генерація DEK / шифрування; політика `worker` — лише розшифрування; KEK не експортується.

```
Rel(api, kms, "Генерує DEK (політика: datakey/encrypt)", "HTTPS, Transit API; Kubernetes auth")
Rel(worker, kms, "Розшифровує DEK (політика: decrypt)", "HTTPS, Transit API; Kubernetes auth")
```

### R4-10 · С · Зони довіри і вихідний трафік воркера не відображені

- **Фрагмент:** L2 — один `System_Boundary(b, ...)` для всіх контейнерів.
- **Підстава:** SRS-NFR-SEC-14 (NetworkPolicy: заборона за замовчуванням; вихід воркера до 0.0.0.0/0, крім Pod CIDR, Service CIDR, 169.254.0.0/16), SRS-NFR-SEC-05 (блокування спеціальних адрес, фіксація IP, 0 редиректів).
- **Проблема:** `worker` — єдиний контейнер з виходом в інтернет на довільні адреси; ця властивість визначає модель загроз SSRF і не відображена. Межі NetworkPolicy не виділені.
- **Виправлення:** розділити межу платформи на вкладені зони; у описі `worker` зазначити SSRF-фільтр. Вихідний проксі не пропонується: SEC-05 реалізується в коді воркера (перевірка адреси після DNS-резолюції і фіксація IP на час з'єднання), SEC-14 — засобами NetworkPolicy.

```
System_Boundary(b, "Платформа гарантованої доставки вебхуків") {
  Boundary(zEdge, "Зона входу", "NetworkPolicy") { ... ingress ... }
  Boundary(zApp, "Прикладна зона", "NetworkPolicy") { ... api, relay, portal ... }
  Boundary(zEgress, "Зона вихідної доставки", "NetworkPolicy: egress 0.0.0.0/0 крім Pod/Service CIDR, 169.254.0.0/16") { ... worker ... }
  Boundary(zData, "Зона даних", "NetworkPolicy: ingress лише з прикладної зони") { ... db, broker, redis ... }
}
```

### R4-11 · С · Маршрути оператора відкриті через ту саму точку входу

- **Фрагмент:** `Rel(operator, api, "Керує середовищами клієнтів", "REST / HTTPS")`.
- **Підстава:** SRS 2.3 (`platform_operator` — створення середовищ клієнтів і квот), SRS-FUN-12, SRS-NFR-SEC-01, SEC-18.
- **Проблема:** маршрути з правами `platform_operator` обслуговуються тим самим контейнером і, за відсутності вхідного контейнера, тією самою точкою входу, що й маршрути середовищ клієнтів. Поверхня атаки на операції найвищого рівня не обмежена мережевим рівнем.
- **Виправлення:** на вхідному контейнері (R4-01) не публікувати маршрути оператора назовні; доступ оператора — через внутрішній Service (`kubectl port-forward`) або окремий хост із обмеженням за IP. Відобразити:

```
Rel(operator, api, "Керує середовищами клієнтів і квотами", "HTTPS через kubectl port-forward (Kubernetes API); Bearer JWT")
```

### R4-12 · С · Відсутня діаграма розгортання

- **Фрагмент:** набір діаграм — лише L1, L2.
- **Підстава:** SRS-DC-09 (Kubernetes, Helm, Terraform, Argo CD, KEDA), SRS-NFR-PERF-06, SRS-NFR-REL-07 (PDB, `terminationGracePeriodSeconds`), SRS-NFR-MNT-04 (Pod Security Admission `restricted`), SRS-NFR-MNT-05, SRS-NFR-SEC-15 (SOPS, шифрування etcd), SRS 5.0 (окремий вузол k6).
- **Проблема:** кількість реплік, PDB, KEDA ScaledObject (читання consumer lag з брокера), CronJob, namespaces, вузол генератора навантаження, Argo CD не відображаються на рівні контейнерів і не мають іншого носія в наборі діаграм.
- **Виправлення:** додати діаграму розгортання C4 (Mermaid `C4Deployment`) з елементами: кластер Kubernetes (один), namespaces (платформа, дані, спостережуваність, провайдер ідентичності, провайдер ключів, стенд), вузол k6 поза бюджетом, S3-сумісне сховище поза кластером; KEDA → брокер («читає consumer lag теми tasks»); Argo CD → Git-репозиторій (Helm-чарти, SOPS).

```
C4Deployment
  Deployment_Node(k8s, "Кластер Kubernetes", "один кластер, без геореплікації") {
    Deployment_Node(nsApp, "namespace platform", "PSA restricted (enforce)") {
      Container(workerD, "Delivery Worker", "Deployment 1–12 реплік, KEDA, PDB minAvailable: 1")
    }
    Deployment_Node(nsData, "namespace data") {
      ContainerQueue(kafkaD, "Kafka", "StatefulSet, 3 брокери, KRaft")
    }
  }
  Deployment_Node(siteStore, "S3-сумісне сховище", "поза кластером, той самий майданчик") {
    ContainerDb(backupD, "Архів pgBackRest", "S3 bucket")
  }
```

### R4-13 · Н · Розмежування ролей СУБД не відображено

- **Фрагмент:** `ContainerDb(db, ...)`, зв'язки `api → db`, `worker → db`, `relay → db`.
- **Підстава:** SRS-NFR-SEC-10 (роль застосунку без UPDATE/DELETE на таблицю аудиту), SRS-NFR-SEC-11 (RLS для PostgreSQL).
- **Проблема:** контейнери звертаються до СУБД без зазначення ролей; принцип найменших привілеїв не простежується.
- **Виправлення:** у підписах зв'язків вказати роль СУБД: `api` — роль застосунку (INSERT в аудит, RLS); `relay` — лише таблиця outbox; `worker` — завдання, спроби, DLQ; міграції — окрема роль DDL (R2-09).
