## 0. Умови рецензування

### 0.1. Шкала критичності

## 1. Критика аргументації (Decision Audit)

### D1-01 · К · Рішення не має рушійних чинників і кількісних сил контексту

- **Фрагмент:** розділ Decision повністю; розділ Context.
- **Підстава:** SRS-DC-06 (вибір механізму фіксується в ADR з урахуванням SRS-NFR-REL-10); SRS-NFR-REL-01, REL-10, FUN-03.4, FUN-10, MNT-01.
- **Проблема:**
  1. Жоден із чотирьох аргументів розділу Decision не посилається на ідентифікатор вимоги і не містить метрики. Порівняння альтернатив не відтворюване: рецензент не може перевірити, за яким критерієм альтернатива 1 переважає альтернативу 3.
  2. Context не містить даних про навантаження механізму: інтенсивність входу завдань у розклад, розмір індексу, горизонт планування, допустиму похибку запуску. Ці величини визначають усі наступні висновки (розділи 2 і 3 звіту).
  3. Вимоги Must, на які безпосередньо впливає механізм (SRS-NFR-REL-01, SRS-FUN-10, інваріант 8.2), у Context не згадано.
- **Виправлення:** додати розділ «Рушійні чинники рішення» перед розділом Alternatives:

| ID | Чинник | Вимога SRS | Метрика / критерій |
|---|---|---|---|
| DD-1 | Збереженість запланованих спроб | REL-01, FUN-10, 8.2 | 0 завдань у стані `scheduled`, для яких після прогону немає запиту в заглушці або запису в DLQ |
| DD-2 | СУБД — джерело істини; відновлення розкладу | REL-10 | відновлення ≤ 60 с після втрати даних Redis |
| DD-3 | Паритет адаптерів | DC-04, MNT-01, EXP-01 | одна реалізація логіки планування для 3 СУБД × 2 брокерів; кількість реалізацій, залежних від адаптера |
| DD-4 | Діапазон і похибка затримки | FUN-03.4 | затримка 0…3 840 с (full jitter) і до 21 600 с (`Retry-After`); похибка запуску ε, p95 ≤ 2 с |
| DD-5 | Ізоляція endpoint-ів | FUN-04.1, FUN-04.4, REL-02 | відкладене завдання не займає слоту обробки і не блокує партицію або чергу |
| DD-6 | Вплив на ресурси | 5.0, PERF-01 | операцій/с до СУБД, Redis, брокера; пам'ять Redis; частка бюджету 2 vCPU / 1 ГБ; вплив на p99 прийому |
| DD-7 | Відповідність обмеженню проєктування | DC-06 | механізм входить до переліку DC-06 |
| DD-8 | Безпека даних | SEC-08, SEC-09, SEC-11 | payload не дублюється в нові сховища; доступ до даних з фільтром за середовищем клієнта |
| DD-9 | Обсяг реалізації для одного розробника | 2.4 | кількість артефактів коду і контрактних тестів |

### D1-02 · В · «Redis дуже швидкий і популярний»

- **Фрагмент:** «Redis дуже швидкий і популярний».
- **Підстава:** DD-6.
- **Проблема:**
  1. Популярність не є властивістю системи і не входить до жодного рушійного чинника.
  2. «Швидкий» не співвіднесено з потрібною інтенсивністю. Потрібна інтенсивність операцій Redis за ПН-1 [розрах, дод. А.3]: Token Bucket прийому 500 оп/с + ліміт частоти доставки на endpoint (SRS-FUN-05.2) 500 оп/с + опитування індексу R ≤ 12 оп/с + записів в індекс 0 (повторів немає) ≈ 1 012 оп/с. У сценарії з 80% тимчасових відмов без розмикання Circuit Breaker: + 400 ZADD/с + 400 ZREM/с ≈ 1 812 оп/с. Виміряна ємність ZADD без конвеєризації — 90 868 оп/с [вимір], тобто навантаження становить 1,1–2,0% ємності.
  3. Для альтернативи 3 потрібна інтенсивність опитування СУБД ≤ 12 запитів/с; виміряна пропускна здатність порожнього опитування PostgreSQL — 10 064 запитів/с на одному з'єднанні [вимір]. Швидкодія не розрізняє альтернативи 1 і 3 і не може бути аргументом вибору.
- **Виправлення:** «Пропускна здатність не є чинником вибору: потрібна інтенсивність операцій механізму становить ≤ 2·10³ оп/с для Redis і ≤ 12 запитів/с для опитування СУБД, що на два порядки нижче за ємність обох сховищ (дод. А.3). Вибір визначають чинники DD-1…DD-5.»

### D1-03 · С · «ZSET ідеально підходить для черг із пріоритетом за часом»

- **Фрагмент:** «ZSET ідеально підходить для черг із пріоритетом за часом».
- **Підстава:** DD-4, DD-6.
- **Проблема:** оцінне судження без властивостей структури даних, які мають значення для рішення: складність, ідемпотентність, пам'ять, блокування.
- **Виправлення:** «Sorted Set (skiplist + хеш-таблиця) надає: вставку `ZADD` за O(log N); вибірку за діапазоном часу `ZRANGE … BYSCORE … LIMIT` за O(log N + M); унікальність члена множини, завдяки якій повторний `ZADD` того самого `{task_id}:{attempt}` не створює дубліката (ідемпотентність відновлення і звірки). Пам'ять — 142 Б на запис для члена у вигляді рядка UUID (36 символів) [вимір]. Обмеження: Lua-скрипт вибірки виконується в однопотоковому циклі подій Redis і блокує інші команди на ≈ 5,1 мкс на елемент [вимір]; один ключ ZSET належить одному hash slot і не масштабується горизонтально в Redis Cluster без шардування ключа (для одного екземпляра на стенді не застосовується).»

### D1-04 · В · «Redis уже є в стеку для Token Bucket, тому новий компонент не потрібен»

- **Фрагмент:** «Redis уже є в стеку для Token Bucket, тому новий компонент не потрібен».
- **Підстава:** SRS-DC-05, SRS-FUN-05.4, SRS-NFR-REL-10; L2: `api -- Token Bucket --> redis`, `worker -- Індекс розкладу --> redis`; L3: `ConfigInvalidation` (Pub/Sub) у тому самому порту.
- **Проблема:**
  1. Твердження коректне щодо одиниць розгортання: Redis входить до інфраструктурного рівня 5.0 через SRS-DC-05, нового StatefulSet не потрібно.
  2. Твердження приховує зміну класу критичності Redis. За SRS-FUN-05.4 Redis для Token Bucket працює в режимі fail-open: втрата даних або недоступність не впливає на коректність. Після ADR-001 недоступність Redis зупиняє своєчасне виконання повторів, а втрата даних вимагає відновлення індексу (SRS-NFR-REL-10).
  3. Вимоги трьох ролей одного екземпляра до конфігурації конфліктують: лічильники Token Bucket допускають витіснення; індекс розкладу вимагає `maxmemory-policy noeviction`. Політика витіснення діє на весь екземпляр; розділення за логічними базами даних її не розділяє.
- **Виправлення:** «Рішення не додає одиниць розгортання, але переводить Redis із класу "допоміжне сховище з режимом fail-open" у клас "компонент шляху доставки з відновлюваним станом". Конфігурація екземпляра: `maxmemory-policy noeviction`; усі ключі Token Bucket мають TTL; `maxmemory` визначається за D3-03. За переповнення пам'яті запис у Redis завершується помилкою: Token Bucket переходить у fail-open (SRS-FUN-05.4), запис в індекс розкладу компенсує звірка з СУБД (D1-07, крок P5).»

### D1-05 · В · «Retry-топіки складні в налаштуванні і не підтримують довільну затримку full jitter»

- **Фрагмент:** «Retry-топіки складні в налаштуванні і не підтримують довільну затримку full jitter».
- **Підстава:** DD-3, DD-4, DD-6.
- **Проблема:**
  1. «Складні в налаштуванні» — невимірюване твердження.
  2. Твердження про неможливість довільної затримки фактично хибне. Затримку d (у секундах) можна розкласти у двійкову суму рівнів 2^k с: повідомлення послідовно проходить теми рівнів, що відповідають одиничним бітам d. Усі повідомлення однієї теми мають однакову затримку, тому порядок у темі збігається з порядком готовності і блокування головним повідомленням не виникає. Похибка — 1 с. Потрібна кількість рівнів [розрах, дод. А.6]: ⌈log₂(3 840 + 1)⌉ = 12 для full jitter; ⌈log₂(21 600 + 1)⌉ = 15 з урахуванням `Retry-After`.
  3. Інженерні обмеження, які мають бути аргументом замість наведених: у середньому 6–7,5 переходів «споживання + публікація» на один повтор; 432–540 реплік партицій лише для тем повторів (12–15 тем × 12 партицій × RF 3); дві різні реалізації для Kafka і RabbitMQ (D2-02, D2-03); дублювання стану розкладу в брокері, через яке звірка з СУБД потрібна і тут (SRS-NFR-REL-10); вплив повідомлень, що очікують, на `lag` KEDA (D2-02).
- **Виправлення:** «Retry-топіки з фіксованими рівнями затримки забезпечують похибку 1 с лише за двійкового розкладу затримки на 12 рівнів (15 з урахуванням `Retry-After` ≤ 21 600 с), що дає 6–7,5 додаткових операцій споживання і публікації на кожен повтор і 432–540 реплік партицій Kafka. Рівні за номером спроби з випадковою затримкою всередині рівня дають похибку до D_n через блокування головним повідомленням (до 3 840 с для n = 7). Механізм потребує окремих реалізацій для Kafka і RabbitMQ.»

### D1-06 · В · «Опитування СУБД створює зайве навантаження на базу»

- **Фрагмент:** «Опитування СУБД створює зайве навантаження на базу».
- **Підстава:** DD-3, DD-6, DD-7.
- **Проблема:**
  1. Базове навантаження СУБД за ПН-1 ≈ 3 565 операторів SQL/с і ≈ 2 020 фіксацій транзакцій/с [оцінка за потоком даних SRS, дод. А.2]. Опитування за альтернативою 3 додає R ≤ 12 запитів/с, тобто ≤ 0,34%. Порожнє опитування за частковим індексом на таблиці з 2·10⁶ рядків займає 0,099 мс [вимір]; 12 опитувань — ≤ 1,2 мс часу СУБД на секунду.
  2. Кількість операцій запису на один повтор для альтернатив 1 і 3 однакова: SRS-NFR-REL-10 зобов'язує записувати `next_attempt_at` у СУБД в обох випадках; цей запис входить до транзакції фіксації спроби. Пакетне захоплення 100 рядків через `FOR UPDATE SKIP LOCKED` займає 3,27 мс (33 мкс на рядок), а умовне захоплення одного рядка — 0,34 мс [вимір]; тобто пакетне захоплення альтернативи 3 на рядок дешевше за поштучне захоплення, яке `DeliverTaskUseCase` виконує в обох альтернативах.
  3. Справжні обмеження альтернативи 3 не названо: відсутність `SKIP LOCKED` у MongoDB; відсутність API блокування рядків у Prisma Client; кросс-середовищний запит в обхід RLS; залежна від СУБД реалізація планування, що вносить систематичну відмінність у порівняння СУБД (SRS-RQ-02); альтернатива 3 відсутня в переліку SRS-DC-06 (D2-04).
- **Виправлення:** «Опитування СУБД додає ≤ 12 запитів/с (≤ 0,34% базового навантаження ПН-1) і не збільшує кількості операцій запису. Альтернативу 3 відхилено з причин: (а) MongoDB не підтримує `SKIP LOCKED`, і захоплення пакета з N завдань потребує N викликів `findOneAndUpdate` з конкуренцією R опитувачів за ті самі документи; (б) реалізація захоплення залежить від СУБД (3 варіанти), що порушує DD-3 і вносить залежну від СУБД складову в результати SRS-RQ-02; (в) SRS-DC-06 не передбачає цього варіанта.»

### D1-07 · К · Рішення не визначає протоколу узгодження СУБД та індексу

- **Фрагмент:** «Час наступної спроби записується в таблицю завдань і в ZSET (score = час). `DueTaskPoller` щосекунди вибирає завдання, для яких настав час, і публікує їх у тему `tasks`.»; L3: `deliver -- "claim, record, reschedule, DLQ" --> repo`, `deliver -- "add(task_id, t)" --> idx`, `poller -- "claimDue (Lua, атомарно)" --> idx`.
- **Підстава:** SRS-NFR-REL-01, SRS-NFR-REL-10, SRS-FUN-10, інваріант 8.2.
- **Проблема:** ADR не визначає: (1) порядку двох записів (СУБД, Redis); (2) семантики захоплення в індексі — вилучення чи оренда; (3) захисту від застарілих і повторних записів індексу; (4) способу виявлення втрати даних Redis; (5) періодичної звірки індексу з СУБД. Без цих елементів рішення не перевіряється щодо SRS-NFR-REL-01 і REL-10; вікна неузгодженості наведено в D3-01. На діаграмі L3 порядок зв'язків `deliver → repo` і `deliver → idx` також не визначено.
- **Виправлення:** додати до розділу Decision протокол P1–P7:

| Крок | Дія | Гарантія |
|---|---|---|
| P1 | `reschedule`: в одній транзакції з записом спроби — `state = 'scheduled'`, `attempt = n + 1`, `next_attempt_at = t`. Після фіксації — `ZADD sched t "{task_id}:{n+1}"`. Помилка або тайм-аут `ZADD` (200 мс) не скасовує транзакції; збільшується `schedule_index_errors_total{op="add"}` | СУБД — джерело істини (REL-10) |
| P2 | `claimDue` (Lua, кожна репліка раз на 1 с, N ≤ 200): перевірка ключа епохи `sched:epoch`; за його відсутності — повернення ознаки `LOST`; інакше `ZRANGE sched -inf now BYSCORE LIMIT 0 N` і для кожного члена `ZADD sched XX (now + lease)`, lease = 30 с | оренда замість вилучення: збій після захоплення не втрачає запису |
| P3 | Публікація в `tasks` із ключем `endpoint_id` (Kafka `acks=all`; RabbitMQ publisher confirm). Після підтвердження — Lua `ackDue`: `ZREM` члена лише за умови, що його score дорівнює значенню оренди | повідомлення повертається до репліки-власника endpoint-а |
| P4 | Споживач: `UPDATE tasks SET state = 'in_flight', lease_until = … WHERE id = ? AND state = 'scheduled' AND attempt = ? AND next_attempt_at <= now()`; 0 змінених рядків — підтвердження повідомлення без доставки | захист від дублікатів і застарілих членів індексу (fencing за номером спроби) |
| P5 | Звірка кожні 60 с (один виконавець за блокуванням `SET sched:lock:reconcile NX PX 55000`): завдання з `state = 'scheduled' AND next_attempt_at <= now() − 5 с` — повторний `ZADD`; завдання з `state = 'in_flight' AND lease_until < now()` — повернення в `scheduled`. | P6 | Відновлення за ознакою `LOST` або під час старту без ключа епохи: блокування; `SET sched:epoch <uuid>`; потокове читання завдань `scheduled` сторінками по 1 000 рядків; конвеєрний `ZADD` | REL-10, ≤ 60 с (D3-04) |
| P7 | Відкладення без збільшення лічильника спроб — паркування endpoint-а (D3-02) | REL-02, FUN-04.4 |

### D2-02 · В · Альтернатива 2 для Kafka: не враховано стан технології 2026 року

- **Фрагмент:** «**Retry-топіки брокера з фіксованими затримками** (`tasks.retry.1m`, `tasks.retry.5m`, … ). Споживач кожної теми чекає, поки мине затримка, і повертає завдання в `tasks`.»
- **Підстава:** DD-3…DD-6; SRS-NFR-PERF-06, SEC-08, REL-10.
- **Проблема і факти:**
  1. Kafka не має вбудованої відкладеної доставки. KIP-1277 «Support Delayed Message in Kafka» має статус «Under Discussion» (остання зміна сторінки — 11.02.2026) і орієнтований на короткі затримки (до ≈ 15 хв) [джерело 6]; діапазону 3 840 с і 21 600 с він не покриває навіть у разі прийняття.
  2. Share groups (KIP-932, «Queues for Kafka») оголошено готовими до промислового використання в Apache Kafka 4.2.0 (17.02.2026) [джерело 4]. Вони надають підтвердження окремих записів і обмеження кількості доставок (за замовчуванням 5 [джерело 5]; потрібно 8), але експоненційна затримка повторної доставки віднесена до планів розвитку [джерело 5]; механізмом відкладення share groups не є. Share consumer у librdkafka 2.15.0 має статус Preview з вимогою не використовувати його в промисловому середовищі [джерело 7]; підтримку share consumer у `@confluentinc/kafka-javascript` **не перевірено**.
  3. Рівні за номером спроби (`retry.1`…`retry.7`) з випадковою затримкою всередині рівня: голова теми з затримкою до D_n блокує готові повідомлення за нею; похибка — до D_n (до 3 840 с) [розрах].
  4. Фіксовані рівні без розкладу (1m, 5m, …) квантують затримку і змінюють розподіл full jitter, заданий SRS-FUN-03.4.
  5. Двійковий розклад (D1-05): 12–15 тем; за 12 партицій і RF 3 — 432–540 реплік партицій на 3 брокерах (144–180 на брокер) плюс 108 реплік тем `events`, `tasks`, poison-DLQ [розрах].
  6. Споживач рівня призупиняє партицію (`pause`) до готовності голови; ребалансування групи скидає це очікування, і новий власник повторно читає голову.
  7. KEDA: повідомлення, що очікують у темах повторів, входять до lag групи споживачів. Для 240 000 повідомлень (10 хв сценарію REL-02) за `lagThreshold` = 1 000 бажана кількість реплік — ⌈240 000 / 1 000⌉ = 240, тобто постійне масштабування до максимуму 12 [розрах]. Теми повторів потрібно виключити з тригера KEDA.
  8. Повідомлення мають містити лише `task_id` і номер спроби: payload у темах повторів не підлягає стиранню за SRS-NFR-SEC-09 до закінчення `retention.ms`.
  9. Стан розкладу дублюється в брокері; за SRS-NFR-REL-10 джерелом істини залишається СУБД, тому звірка (аналог P5) потрібна і в цій альтернативі.
- **Виправлення:** замінити опис альтернативи 2 у розділі Alternatives текстом з пп. 1–9 у скороченому вигляді (Додаток В).

### D2-03 · В · Альтернатива 2 для RabbitMQ: не враховано стан плагіна і семантику TTL

- **Фрагмент:** той самий; брокер RabbitMQ є параметром SRS-EXP-01.
- **Підстава:** SRS-NFR-REL-05 (quorum queues), DD-3.
- **Проблема і факти:**
  1. Плагін `rabbitmq-delayed-message-exchange` більше не підтримується командою RabbitMQ; репозиторій архівовано [джерело 8]. Відкладені повідомлення зберігаються в таблиці Mnesia з однією дисковою реплікою на поточному вузлі; втрата вузла втрачає повідомлення; дизайн не призначений для великої кількості відкладених повідомлень; Mnesia вилучено з RabbitMQ у циклі розробки 4.3.0 [джерело 8]. Плагін несумісний із SRS-NFR-REL-05 і SRS-NFR-REL-01.
  2. Механізм TTL + dead-letter exchange: TTL окремого повідомлення спрацьовує лише тоді, коли повідомлення досягає голови черги [джерело 9]; per-message TTL для випадкової затримки дає блокування головним повідомленням (як D2-02, п. 3). Застосовний варіант — окрема черга на кожен рівень із TTL черги (12–15 quorum queues × 3 репліки). Quorum queues перенаправляють прострочені повідомлення до dead-letter exchange, коли ті досягають голови [джерело 9]. Налаштування гарантії at-least-once для dead-lettering у quorum queues **не перевірено** в межах звіту.
  3. Реалізація для RabbitMQ відрізняється від реалізації для Kafka (TTL черги проти `pause` партиції), що подвоює код і контрактні тести SRS-NFR-MNT-01.
- **Виправлення:** «Для RabbitMQ альтернатива 2 реалізується лише чергами очікування з TTL черги і dead-letter exchange (12–15 quorum queues); плагін відкладених повідомлень не розглядається через припинення підтримки, зберігання в одній репліці і вилучення Mnesia з RabbitMQ 4.3.»

### D2-04 · В · Альтернатива 3: пропущені обмеження і пропущені переваги

- **Фрагмент:** «**Опитування таблиці завдань у СУБД** (`WHERE next_attempt_at <= now() ORDER BY next_attempt_at LIMIT N FOR UPDATE SKIP LOCKED`) без Redis.»; «Опитування СУБД створює зайве навантаження на базу.»
- **Підстава:** DD-1…DD-9; SRS-DC-04, SEC-11, RQ-02.
- **Пропущені обмеження:**
  1. **MongoDB.** Аналога `SKIP LOCKED` немає; `findOneAndUpdate` змінює один документ, обраний за `filter` і `sort` [джерело 13]. Захоплення пакета з N завдань — N викликів. R опитувачів із тим самим `sort: {next_attempt_at: 1}` конкурують за ті самі документи; потрібне розбиття простору завдань між опитувачами (наприклад, `hash(task_id) mod R`), яке змінюється разом із кількістю реплік KEDA.
  2. **MySQL.** `SKIP LOCKED` підтримується InnoDB з MySQL 8.0; підтримку MySQL 8.0 завершено 30.04.2026 [джерело 12]; у домені SRS-EXP-01 слід фіксувати MySQL 8.4 LTS.
  3. **Prisma.** Prisma Client не надає API для `SELECT … FOR UPDATE SKIP LOCKED`; потрібен `$queryRaw` з окремим SQL для PostgreSQL і MySQL (**не перевірено** за поточною документацією Prisma в межах звіту).
  4. **RLS.** Опитувач читає завдання всіх середовищ клієнтів; SRS-NFR-SEC-11 вимагає фільтра за ідентифікатором середовища клієнта з облікових даних (D3-06).
  5. **PostgreSQL.** Оновлення індексованого стовпця `next_attempt_at` виключає HOT-оновлення; частковий індекс `WHERE state = 'scheduled'` змінюється за кожного переходу стану; потрібне налаштування autovacuum для таблиці завдань. Те саме стосується А1, оскільки за SRS-NFR-REL-10 `next_attempt_at` зберігається в СУБД і індексується для P5/P6.
  6. **Експеримент.** Реалізація захоплення відрізняється для трьох СУБД; різниця потрапляє в результати SRS-RQ-02 як складова порівняння СУБД.
  7. **SRS-DC-06** не передбачає цього варіанта.
- **Пропущені переваги:** відсутній подвійний запис (D3-01 не виникає); SRS-NFR-REL-10 виконується без відновлення індексу; Redis залишається в класі fail-open (D1-04); не потрібні нові метрики індексу; обсяг реалізації ≈ 5 артефактів проти ≈ 8.
- **Виправлення:** внести пп. 1–7 і перелік переваг до опису альтернативи 3 (Додаток В).

Відхиляється.
  2. **А4б. pg-boss, graphile-worker.** Працюють лише з PostgreSQL; суперечать SRS-DC-04. Відхиляються.
  3. **А5. Гібрид із вікном.** СУБД — джерело істини; індекс Redis містить лише завдання з `next_attempt_at ≤ now + H`; звірка P5 щохвилини довантажує наступне вікно. Пам'ять обмежена величиною λ·H незалежно від тривалості відмови: для λ = 400 завдань/с і H = 10 хв — 240 000 записів ≈ 34 МБ [розрах + вимір]; відновлення охоплює одне вікно. Ціна — ще один стан запису завдання і довантаження вікна.
  4. **А6. Таймерне колесо в пам'яті репліки-власника партиції.** Redis не потрібен; перехід власності партиції під час ребалансування і масштабування KEDA вимагає перезавантаження вікна з СУБД. Обсяг реалізації для одного розробника — найбільший; рекомендовано лише згадати як відхилену.
  5. Брокери з вбудованою відкладеною доставкою поза SRS-DC-04 не розглядаються; це слід зазначити одним реченням.
- **Виправлення:** додати А4 і А5 до розділу Alternatives; А4б, А6 — у перелік відхилених без детального аналізу.

### D2-06 · С · Недоліки обраної альтернативи відсутні в розділі Alternatives

- **Фрагмент:** «1. **Redis ZSET як індекс розкладу + СУБД як джерело істини.** …» (без недоліків).
- **Проблема:** для альтернативи 1 не вказано: подвійний запис і вікна неузгодженості (D3-01); зміна класу критичності Redis (D1-04); відновлення і звірка (D3-04); блокування Lua-скриптом (D3-05); пам'ять O(λ·W) (D3-03); ліцензійний ризик (D3-10).
- **Виправлення:** перелік недоліків — у Додатку В.

### D2-07 · Н · Ряд затримок і термінологія альтернативи 2

- **Фрагмент:** «`tasks.retry.1m`, `tasks.retry.5m`, … »; «повертає завдання в `tasks`»; «публікує їх у тему `tasks`».
- **Проблема:** ряд 1m, 5m не відповідає ряду D_n = 60 · 2^(n−1) с (60, 120, 240, …); термін «тема» не застосовний до RabbitMQ.
- **Виправлення:** «рівні `tasks.delay.2^k` (k = 0…11 або 0…14)»; «тема (Kafka) / черга (RabbitMQ) `tasks`».

## 3. Аудит наслідків (Consequences Trade-off)

### D3-01 · К · Вікна неузгодженості подвійного запису: завдання без запису в індексі

- **Фрагмент:** «**Негативні:** — потрібно відновлювати індекс після втрати Redis.»; `desc_22.md`, ScheduleIndexRebuilder: «Під час старту і за ознакою втрати даних Redis відновлює індекс розкладу з СУБД».
- **Підстава:** SRS-NFR-REL-01 (0 втрат за відмови pod-а воркера), SRS-FUN-10, інваріант 8.2, SRS-NFR-REL-10.
- **Проблема:** запис у СУБД і запис у Redis не атомарні. Вікна:

| Вікно | Подія | Стан після збою | Наслідок без звірки |
|---|---|---|---|
| W1 | фіксація P1 у СУБД → збій pod-а або тайм-аут до `ZADD` | `scheduled` у СУБД, запису в індексі немає; дані Redis не втрачено | ознаки втрати немає, відновлення не запускається, повтор не виконується ніколи |
| W2 | захоплення з вилученням (`ZREM` у Lua) → збій до підтвердження брокера | запису в індексі і повідомлення в брокері немає | те саме |
| W3 | `ZADD` завершився на сервері, клієнт отримав тайм-аут і повторив | один член множини (ідемпотентність) | наслідків немає |
| W4 | застарілий член `{task}:{n}` після переходу до спроби n+1 | два члени для одного завдання | дублікат публікації; без P4 — повторна спроба з неправильним номером |
| W5 | публікація підтверджена, `ackDue` не виконано | оренда спливає, повторна публікація | дублікат повідомлення; P4 відкидає його без доставки |

  Сценарій RTM для SRS-NFR-REL-01 (`kubectl delete pod` воркера під навантаженням) може потрапити у вікна W1 і W2. Інваріант 8.2 не допускає жодного завдання без запиту в заглушці або запису в DLQ; одне завдання у вікні W1 або W2 дає результат fail.
- **Виправлення:**
  1. Протокол P1–P6 (D1-07): оренда замість вилучення (усуває W2), fencing за номером спроби (W4, W5), звірка кожні 60 с (W1).
  2. Негативний наслідок у ADR: «Запис у СУБД і в індекс не атомарний. Завдання, запис якого в індекс не виконано, повторюється не пізніше ніж через 60 с + 5 с після запланованого часу за рахунок звірки P5; лічильник `schedule_reconciled_total` фіксує такі випадки.»
  3. Тест рівня PR: адаптер-дублер `ScheduleIndex`, що завершується помилкою після фіксації P1 і після P2; критерій — завдання доставлене в межах модельного часу звірки. Рядок RTM для SRS-NFR-REL-01 доповнити перевіркою `schedule_reconciled_total`.
  4. Діаграма L3: підпис `rebuild` — «Відновлення: старт · втрата епохи · звірка кожні 60 с».

### D3-02 · К · Рециркуляція відкладених завдань і необмежене зростання індексу

- **Фрагмент:** «однакова поведінка для Kafka і RabbitMQ»; розділ Consequences не розглядає відкладень без збільшення лічильника спроб; L3: AdmissionChain → відкладення.
- **Підстава:** SRS-NFR-REL-02 (деградація p95 для 9 середовищ клієнтів ≤ 10%), SRS-FUN-04.4, SRS-FUN-06.3, бюджет 5.0.
- **Проблема:** якщо кожне відкладене завдання проходить через індекс розкладу (поточна модель L3), у сценарії SRS-NFR-REL-02 [розрах, дод. А.5]:
  1. Вхід у відкладення λ_def = 400 завдань/с; Circuit Breaker у стані Open не збільшує лічильника спроб (SRS-FUN-04.4), тому завдання не досягають DLQ. Кількість відкладених завдань N(t) = 400·t; через 600 с — 240 000.
  2. Якщо час пробудження — момент переходу до Half-Open (60 с) або випадковий у межах 60 с, усі відкладені завдання повертаються в обробку в середньому раз на 60 с: r(t) = N(t)/60; через 600 с r = 4 000 завдань/с; за 10 хв — 1,2·10⁶ циклів.
  3. Кожен цикл: частка `claimDue`, публікація, споживання, `UPDATE` захоплення і `UPDATE` повторного відкладення в СУБД, `ZADD`. Наприкінці прогону: СУБД + 8 000 операторів/с проти базових ≈ 3 565 (у 3,2 раза більше); брокер + 4 000 повідомлень/с проти базових 1 000; ЦП воркера r·c, де c — вартість циклу [оцінка: c = 100–200 мкс] — 0,4–0,8 vCPU, тобто 20–40% бюджету 2 vCPU; lag `tasks` зростає, KEDA масштабує воркер до 12 реплік.
  4. Наслідок — деградація доставки для 9 інших середовищ клієнтів; виконання SRS-NFR-REL-02 під загрозою.
  5. Поза прогоном: до автоматичного вимкнення endpoint-а через 72 год (SRS-FUN-06.3) індекс накопичує 400 × 259 200 = 1,04·10⁸ записів ≈ 14,7 ГБ [розрах за 142 Б/запис].
- **Виправлення:** паркування endpoint-а:
  1. Для стану Open Circuit Breaker, блокування `OrderingGate` і стану `disabled` завдання не повертаються в брокер: у СУБД — `state = 'parked'`; в індексі — один запис на endpoint `ep:{endpoint_id}` зі score = час переходу до Half-Open. Кількість записів ≤ кількості endpoint-ів: ≤ 100 на середовище клієнта (SRS-NFR-SEC-18), ≤ 1 000 для 10 середовищ ≈ 142 КБ.
  2. `RouteEventUseCase` для endpoint-а в стані Open створює завдання одразу в стані `parked` без публікації в `tasks` (економія 400 публікацій/с у сценарії REL-02).
  3. Після переходу Circuit Breaker у Closed `ResumeParkedUseCase` переводить завдання endpoint-а в `scheduled` сторінками за порядком прийому з інтенсивністю, не більшою за ліміти Bulkhead і частоти endpoint-а; порядок для `ordered = true` зберігається.
  4. Відкладення за лімітом частоти (SRS-FUN-05.2) і переповненням Bulkhead — поштучні на час до наступного токена, обчислений Token Bucket; за черги endpoint-а понад поріг (наприклад, 1 000 завдань) — паркування.
  5. Діаграма L3: компонент `EndpointParking` (Application) зі зв'язками до `EndpointState`, `ScheduleIndex`, `TaskRepository`; підпис зв'язку `admission`: «відмова → park | defer(t)».

### D3-03 · В · Зміна класу критичності Redis: пам'ять, політика витіснення, збереження

- **Фрагмент:** «**Негативні:** — потрібно відновлювати індекс після втрати Redis.»; L2: `redis["Redis 7, Lua · Token Bucket; похідний індекс розкладу; інвалідація кешу"]`.
- **Підстава:** SRS-NFR-REL-10, SRS-FUN-05.4, бюджет 5.0.
- **Проблема:** не оцінено розмір індексу і не визначено конфігурації Redis. Розмір за законом Літтла L = λ·W, 142 Б/запис [вимір; розрах, дод. А.4]:

| Сценарій | λ, завдань/с | W, с | L, записів | Пам'ять |
|---|---|---|---|---|
| ПН-1 | 0 | — | 0 | 0 |
| 1% тимчасових відмов, успіх на 2-й спробі | 5 | 30 | 150 | ≈ 21 КБ |
| REL-02, 10 хв, поштучне відкладення (без D3-02) | 400 | 600 | 240 000 | 34 МБ (виміряно 34,1 МБ) |
| 80% стійких відмов без розмикання CB, стаціонарний стан | 400 | 3 810 | 1 524 000 | 216 МБ |
| 100% стійких відмов, стаціонарний стан | 500 | 3 810 | 1 905 000 | 270 МБ (виміряно 270,1 МБ) |
| `Retry-After` = 21 600 с перед кожним із 7 повторів | 400 | 151 200 | 60 480 000 | 8,6 ГБ |
| REL-02 з паркуванням (D3-02) | — | — | ≤ 1 000 | ≤ 142 КБ |

- **Виправлення:**
  1. Конфігурація: `maxmemory-policy noeviction` (D1-04); `maxmemory` ≥ 1,5 × 216 МБ ≈ 324 МБ, рекомендовано 512 МБ; оповіщення за використання > 70% `maxmemory`.
  2. Збереження: AOF з `appendfsync everysec` зменшує частоту повних відновлень після перезапуску pod-а Redis; коректність від нього не залежить (P5, P6).
  3. Для сценарію довгих `Retry-After` — гібрид із вікном (А5, D2-05), що обмежує пам'ять λ·H.
  4. Негативний наслідок у ADR: «Redis отримує стан, що вимагає `noeviction`, обсягу пам'яті до 270 МБ у стаціонарному стані повної відмови отримувачів і постійного тому для AOF; недоступність Redis затримує повтори до відновлення доступності і виконання звірки P5, але не призводить до їх втрати.»

### D3-04 · В · Відновлення індексу ≤ 60 с: здійсненність і вплив на бюджет 1 ГБ

- **Фрагмент:** «потрібно відновлювати індекс після втрати Redis»; L3: `rebuild -- "findDue посторінково" --> repo`, `rebuild -- "add ідемпотентно" --> idx`.
- **Підстава:** SRS-NFR-REL-10, бюджет 5.0 (2 vCPU, 1 ГБ сумарно для API, ретранслятора і воркерів).
- **Проблема:**
  1. Потрібна швидкість відновлення L/60: 4 000 записів/с (REL-02, 10 хв); 25 400 (80% стійких відмов); 31 750 (100%) [розрах]. Redis не є вузьким місцем: конвеєрний ZADD — 254 453 оп/с [вимір], 1,9·10⁶ записів — ≈ 7,5 с. Швидкість читання з СУБД і десеріалізації в Node.js **не виміряно**; для Prisma Client з повними об'єктами моделі вона може стати обмеженням.
  2. Завантаження всього розкладу в пам'ять: 1,9·10⁶ рядків × ≈ 250 Б на об'єкт JavaScript ≈ 475 МБ [оцінка] — понад частку одного воркера в бюджеті 1 ГБ; наслідок — OOMKilled і циклічний перезапуск відновлення.
  3. Не визначено способу виявлення втрати даних і точки вимірювання 60 с.
  4. Після відновлення прострочені завдання вивільняються зі швидкістю R·N за секунду (до 12 × 200 = 2 400/с) — сплеск навантаження на отримувачів і СУБД.
  5. Планувальник фонових завдань (CronJob, L2) не придатний для відновлення: мінімальний період CronJob — 1 хв, плюс час запуску pod-а; 60 с не гарантуються.
- **Виправлення:**
  1. Відновлення виконує воркер (P6): `$queryRaw` або курсор драйвера, лише стовпці `id`, `attempt`, `next_attempt_at`; keyset-пагінація по 1 000 рядків (≈ 250 КБ на сторінку); конвеєрний `ZADD`.
  2. Виявлення: ключ `sched:epoch`, перевірка в кожному виклику `claimDue` — затримка виявлення ≤ 1 с.
  3. Визначення в ADR: «Час відновлення — інтервал від `FLUSHALL` до моменту, коли `ZCARD sched` ≥ кількості завдань `scheduled` у СУБД на момент `FLUSHALL` і опубліковано перше прострочене завдання; ціль ≤ 60 с; метрика `schedule_rebuild_duration_seconds`.»
  4. Обмеження швидкості вивільнення прострочених завдань після відновлення: сумарно ≤ 500 завдань/с (параметр розділу 7.1).
  5. Вимірювання швидкості відновлення 1,9·10⁶ записів для кожної СУБД — у кампанії E (рядок RTM SRS-NFR-REL-10).

### D3-05 · В · Блокування Redis Lua-скриптом і вплив на латентність прийому

- **Фрагмент:** L3: `poller -- "claimDue (Lua, атомарно)" --> idx`; L2: один екземпляр Redis для `api` (Token Bucket) і `worker`.
- **Підстава:** SRS-NFR-PERF-01 (p99 ≤ 250 мс), SRS-DC-05.
- **Проблема:** Lua-скрипт виконується атомарно в однопотоковому циклі подій Redis; команди Token Bucket API прийому очікують його завершення. Виміряний час `claimDue` з орендою на ZSET з 10⁶ записів [вимір]: N = 100 — 0,52 мс; N = 500 — 2,57 мс; N = 1 000 — 5,11 мс (≈ 5,1 мкс на елемент). За N = 1 000 і R = 12 реплік — до 61 мс зайнятості Redis на секунду (6,1%) і разове очікування до 5,1 мс; рециркуляція D3-02 (4 000 елементів/с) додає ≈ 20 мс/с. Вплив на p99 прийому — частки відсотка бюджету 250 мс за умови обмеження N; без обмеження N (вибірка всіх прострочених після відновлення: 10⁵ записів ≈ 0,5 с) — порушення SRS-NFR-PERF-01 на час виконання.
- **Виправлення:** «Розмір пакета N обирається з умов N·R ≥ λ_due,max і t_script(N) ≤ 2 мс; базове значення N = 200 (≈ 1,1 мс). Скрипти не виконують вибірок без `LIMIT`. Фази опитування реплік зсунуті випадковим зміщенням у межах 1 с. Увімкнено `latency-monitor-threshold 5`.»

### D3-06 · В · Безпека: RLS, ACL Redis, TLS, мінімізація даних індексу

- **Фрагмент:** відсутній у Consequences; L2: `worker -- "Індекс розкладу [RESP/TCP]" --> redis`; L3: `rebuild -- "findDue посторінково" --> repo`; `desc_22.md`: «`environmentId` — обов'язковий параметр; RLS для PostgreSQL».
- **Підстава:** SRS-NFR-SEC-11, SEC-08, SEC-09, SEC-14.
- **Проблема:**
  1. Звірка P5 і відновлення P6 читають завдання всіх середовищ клієнтів. SRS-NFR-SEC-11 вимагає фільтра за ідентифікатором середовища клієнта з облікових даних; для PostgreSQL — RLS. ADR не визначає, як ці запити проходять RLS.
  2. Не зафіксовано склад члена індексу; за наявності в ньому payload або URL endpoint-а Redis стає сховищем персональних даних для SEC-08/09.
  3. Права облікового запису воркера в Redis не визначено; сценарій RTM SRS-NFR-REL-10 використовує `FLUSHALL`.
  4. Зв'язок RESP на L2 без TLS і без автентифікації.
- **Виправлення:**
  1. Звірка і відновлення виконуються в циклі за середовищами клієнтів із встановленням `app.environment_id` для кожної сторінки (10 запитів на прохід для 10 середовищ) — без винятку з SEC-11. Альтернатива — окрема роль СУБД з `BYPASSRLS` і правами `SELECT (id, attempt, next_attempt_at, state)` на таблицю завдань, зафіксована в ADR як виняток із SEC-11 з обґрунтуванням. Для MySQL і MongoDB — фільтр рівня адаптера.
  2. «Член індексу — `{task_id}:{attempt}`; payload, ідентифікатори середовищ клієнтів і URL endpoint-ів в індекс не записуються; Redis не є сховищем у розумінні SRS-NFR-SEC-08/09.»
  3. ACL-користувач воркера: команди `ZADD`, `ZRANGE`, `ZREM`, `ZCARD`, `EVALSHA`, `EVAL`, `SET`, `GET`, `EXISTS`, `PUBLISH`, `SUBSCRIBE` на шаблони ключів `sched:*`, `ep:*`, `rl:*` і канали `cfg:*`; заборонено `FLUSHALL`, `FLUSHDB`, `CONFIG`, `KEYS`. `FLUSHALL` у кампанії E виконує окремий адміністративний обліковий запис Job-а експерименту.
  4. Зафіксувати рішення щодо RESP: TLS або обмеження NetworkPolicy (SEC-14) з явним обґрунтуванням; підпис зв'язків L2 доповнити «ACL».

### D3-07 · В · «Точна затримка full jitter без округлення» — недоведений позитивний наслідок

- **Фрагмент:** «точна затримка full jitter без округлення».
- **Підстава:** SRS-FUN-03.4; RTM (рядок SRS-FUN-03.4 перевіряє обчислену затримку з інжектованими портами годинника і генератора, а не фактичну).
- **Проблема:** фактичний момент спроби t_fact = t_fail + d + δ_poll + δ_pub + δ_q + δ_adm, де δ_poll ∈ [0; 1 с] — період опитування; δ_pub — підтвердження брокера; δ_q — черга партиції (lag / швидкість споживання); δ_adm — відкладення AdmissionChain. Похибка альтернативи 1 (δ_poll ≤ 1 с) не відрізняється від альтернативи 3 (той самий період) і від двійкового розкладу альтернативи 2 (рівень 1 с). Фактичну похибку не вимірює жоден тест.
- **Виправлення:** «Планова затримка d обчислюється без квантування. Фактична затримка перевищує d на ε = δ_poll + δ_pub + δ_q, δ_poll ≤ 1 с; ціль — ε p95 ≤ 2 с за ПН-1 з ін'єкцією 5xx у 10% відповідей заглушки. Метрика — гістограма `schedule_dispatch_lag_seconds` = (час публікації в `tasks`) − `next_attempt_at`, межі кошиків 0,1; 0,25; 0,5; 1; 2; 5; 10.» Додати рядок RTM (етап E).

### D3-08 · С · «Мінімальне навантаження на СУБД» — наслідок не розрізняє альтернатив

- **Фрагмент:** «мінімальне навантаження на СУБД».
- **Проблема:** операції СУБД на один повтор [розрах, дод. А.7]:

| Операція | А1 | А2 | А3 |
|---|---|---|---|
| Запис `next_attempt_at` (у транзакції спроби) | 1 (обов'язково за REL-10) | 1 | 1 |
| Захоплення перед спробою | 1 поштучне `UPDATE` | 1 поштучне `UPDATE` | 1/N пакетного `UPDATE … SKIP LOCKED` |
| Фонові запити | 1 запит звірки / 60 с; повне читання під час відновлення | звірка (аналог P5) | R ≤ 12 запитів/с |

  Різниця між А1 і А3 — ≤ 12 запитів читання/с (≤ 0,34% базового навантаження).
- **Виправлення:** «Механізм не додає операцій запису в СУБД понад обов'язкові за SRS-NFR-REL-10; фонові читання — один запит звірки за 60 с і повне читання розкладу під час відновлення.»

### D3-09 · С · «Простий код» — твердження не підтверджене

- **Фрагмент:** «простий код».
- **Проблема:** альтернатива 1 з протоколом P1–P7 містить ≈ 8 артефактів (дод. А.8): порт `ScheduleIndex` і адаптер; Lua-скрипти `claimDue`, `ackDue`; `DueTaskPoller`; `ScheduleReconciler`; `ScheduleIndexRebuilder` з блокуванням і ключем епохи; контрактні тести і тести відмов адаптера; сценарій `FLUSHALL` кампанії E. Альтернатива 3 — ≈ 5 артефактів.
- **Виправлення:** вилучити з позитивних наслідків; до нейтральних: «Обсяг реалізації — ≈ 8 артефактів проти ≈ 5 для опитування СУБД; додаткова складність компенсує незалежність логіки планування від СУБД (DD-3).»

### D3-10 · С · Vendor lock-in, ліцензування, образи і клієнтська бібліотека

- **Фрагмент:** L2: `redis["Redis · [Redis 7, Lua]"]`; ADR не вказує дистрибутива і версії.
- **Підстава:** SRS-DC-05, DC-09, SEC-06, SEC-17.
- **Факти:**
  1. Redis ≤ 7.2 — BSD-3-Clause; Redis 7.4–7.8 — RSALv2 або SSPLv1; Redis ≥ 8.0 — на вибір RSALv2, SSPLv1 або AGPLv3 [джерело 1]. Позначення «Redis 7» не визначає ліцензії.
  2. Valkey 9.0 — загальнодоступний випуск 21.10.2025, ліцензія BSD, проєкт Linux Foundation [джерело 2].
  3. Bitnami з 28.08.2025 перемістив версіоновані образи до `bitnamilegacy` без подальших оновлень; безкоштовні образи `bitnamisecure` — лише тег `latest` і лише для розробки [джерело 10]. Helm-чарт Bitnami з фіксованою версією в Argo CD означає образ без виправлень безпеки.
  4. Офіційний Helm-чарт Valkey (`valkey-io/valkey-helm`) опубліковано 06.01.2026 у зв'язку зі змінами Bitnami; підтримує збереження, реплікацію, ACL, TLS, експортер Prometheus [джерело 3].
  5. ioredis 6.x: супровід «на основі найкращих зусиль»; для нових проєктів рекомендовано node-redis [джерело 11].
- **Проблема:** ризик прив'язки — ліцензійний і операційний (джерело образів), а не функціональний: використовувані команди підтримують і Redis, і Valkey.
- **Виправлення:**
  1. «Дистрибутив: Valkey 9.x (BSD-3) — базовий; сумісність перевіряється також із Redis 8.x (AGPLv3). Розгортання — офіційний чарт Valkey з фіксованими версіями чарта й образу; чарти Bitnami не використовуються.»
  2. «Набір команд порту `ScheduleIndex` обмежено командами, наявними в Redis 7.2 і Valkey: `ZADD` (`XX`, `GT`), `ZRANGE … BYSCORE … LIMIT`, `ZREM`, `ZCARD`, `EVALSHA`/`EVAL`, `SET … NX PX`, `EXISTS`; модулі Redis не використовуються.»
  3. Вибір клієнта (ioredis або node-redis) зафіксувати з урахуванням п. 5; залежність ізольована адаптером (правило dependency-cruiser: імпорт клієнта Redis лише з `src/adapters/**`).
  4. Підпис L2: «Redis [Valkey 9, Lua]».

### D3-13 · С · FinOps: резервування ресурсів

- **Фрагмент:** відсутній у Consequences.
- **Проблема:**
  1. В одному кластері пам'ять Redis — зарезервована ємність вузла. `maxmemory` 512 МБ з урахуванням фрагментації (1,08 [вимір]) і копіювання сторінок під час перезапису AOF (до двократного зростання на час перезапису за документацією Redis; кількісно **не перевірено**) дає ліміт pod-а ≈ 1 ГБ — величину, рівну всьому бюджету прикладного рівня 5.0.
  2. Альтернатива 3 не потребує пам'яті Redis; частковий індекс PostgreSQL для 250 000 завдань `scheduled` — 5,5 МБ [вимір].
  3. Поштучне відкладення (без D3-02) або довгі `Retry-After` вимагають 8,6–14,7 ГБ (D3-02, D3-03), що виходить за межі будь-якого розумного резервування для стенда.
  4. Для керованих хмарних сервісів: ElastiCache for Valkey має ціну на 20% нижчу (вузлова модель) і на 33% нижчу (serverless) за інші рушії [джерело 14]; застосовно лише за перенесення поза один кластер.
- **Виправлення:** «Інфраструктурний рівень 5.0 доповнюється резервуванням пам'яті Redis: requests = limits = 1 ГБ за `maxmemory` 512 МБ. Розмір індексу обмежено паркуванням endpoint-ів (D3-02); за потреби обмеження незалежно від тривалості відмов — варіант із вікном (А5).»

### D3-14 · Н · Взаємодія з KEDA

- **Фрагмент:** «однакова поведінка для Kafka і RabbitMQ».
- **Проблема:** повторно опубліковані завдання входять до lag `tasks` і впливають на масштабування KEDA (`lagThreshold` = 1 000); для RabbitMQ (`mode: QueueLength`) — аналогічно. Без D3-02 рециркуляція масштабує воркер до 12 реплік.
- **Виправлення:** «Повторно опубліковані завдання враховуються в lag `tasks`; за паркування endpoint-ів їхня інтенсивність обмежена інтенсивністю повторів.» Позитивний наслідок «однакова поведінка» уточнити: «логіка планування не залежить від брокера; повторна публікація використовує ключ `endpoint_id` (Kafka — партиція, RabbitMQ — consistent-hash exchange).»

### D3-15 · Н · Зростання частки дублікатів

- **Фрагмент:** відсутній у Consequences.
- **Проблема:** оренда (P2) і звірка (P5) створюють повторні повідомлення `tasks`; P4 відкидає їх без HTTP-запиту. Дублікат HTTP-запиту можливий лише за збою pod-а між надсиланням запиту і фіксацією результату — властивість at-least-once (SRS-FUN-10).
- **Виправлення:** «Частка дублікатів вимірюється окремо (SRS 8.2) і не є критерієм відмови; за ПН-1 без ін'єкцій очікуване значення — 0.»

### D3-16 · Н · Умови перегляду рішення відсутні

- **Виправлення:** «Рішення переглядається, якщо: (а) KIP-1277 прийнято з підтримкою затримок ≥ 21 600 с і підтримкою в клієнті `@confluentinc/kafka-javascript`; (б) share groups отримують затримку повторної доставки в стабільному JS-клієнті; (в) Redis вилучено зі стека (зміна SRS-DC-05) — перехід до альтернативи 3; (г) виміряний час відновлення > 60 с — перехід до варіанта з вікном (А5).»

## Додаток А. Розрахунки

### А.1. Горизонт повторів

D_n = min(21 600, 60 · 2^(n−1)), n = 1…7: 60 + 120 + 240 + 480 + 960 + 1 920 + 3 840 = 7 620 с (2,12 год). Для full jitter E[затримки] = D_n/2, ΣE = 3 810 с (63,5 хв). D_8 = 7 680 с і D_9 = 15 360 с теж менші за cap; cap обмежує лише `Retry-After`. З `Retry-After` = 21 600 с перед кожним повтором: 7 × 21 600 = 151 200 с (42 год).

### А.2. Базове навантаження СУБД за ПН-1 [оцінка за потоком даних SRS]

| Компонент | Оператори | Операторів/с | Фіксацій/с |
|---|---|---|---|
| API прийому | ключ ідемпотентності, подія, outbox (1 транзакція) | 3 × 500 = 1 500 | 500 |
| Ретранслятор (2 репліки, інтервал 100 мс) | вибірка `SKIP LOCKED` + позначення опублікованих | 20 + 20 = 40 | 20 |
| Маршрутизація | читання підписок за 5% промахів кешу; вставка завдань | 25 + 500 = 525 | 500 |
| Доставка | захоплення; запис спроби + оновлення стану (1 транзакція) | 500 + 1 000 = 1 500 | 1 000 |
| **Разом** | | **≈ 3 565** | **≈ 2 020** |

Опитування альтернативи 3: R ≤ 12 запитів/с → 12 / 3 565 = 0,34%.

### А.3. Операції Redis за ПН-1

Token Bucket прийому 500 + ліміт частоти endpoint-а 500 + `claimDue` R ≤ 12 + `ZADD` 0 = 1 012 оп/с; з 80% тимчасових відмов без розмикання CB: + 400 `ZADD` + 400 `ackDue` = 1 812 оп/с. Ємність (вимір): `ZADD` без конвеєризації — 90 868 оп/с; з конвеєризацією 16 — 254 453 оп/с. Завантаження — 1,1–2,0%.

### А.4. Пам'ять ZSET

Виміряно приріст `used_memory` на запис: член — рядок UUID (36 символів) — 142 Б (N = 10⁵…1,9·10⁶, стабільно 141–144 Б); член `{uuid}:{attempt}` (38 символів) — 141 Б; член 16 символів — 125 Б. Фрагментація — 1,08. Розміри сценаріїв — таблиця D3-03.

### А.5. Рециркуляція поштучних відкладень (сценарій REL-02)

N(t) = λ_def · t = 400·t; r(t) = N(t)/T_wake, T_wake = 60 с. N(600) = 240 000; r(600) = 4 000 завдань/с. Кількість циклів за 600 с: ∫₀⁶⁰⁰ 400t/60 dt = (400/60) · 600²/2 = 1 200 000. Операції циклу: 2 `UPDATE` СУБД, 1 публікація, 1 споживання, 1 `ZADD`, частка `claimDue` → наприкінці прогону + 8 000 операторів СУБД/с, + 4 000 повідомлень/с. ЦП воркера: r·c; c = 100–200 мкс [оцінка, вимірюється профілюванням] → 0,4–0,8 vCPU. Накопичення до вимкнення endpoint-а (72 год): 400 × 259 200 = 103 680 000 записів × 142 Б ≈ 14,7 ГБ.

### А.6. Теми повторів

Двійковий розклад: кількість рівнів K = ⌈log₂(d_max + 1)⌉: d_max = 3 840 → 12; d_max = 21 600 → 15. Середня кількість переходів для рівномірної затримки ≈ K/2 = 6–7,5. Реплік партицій: 12 × 12 × 3 = 432; 15 × 12 × 3 = 540; плюс `events`, `tasks`, poison-DLQ: 3 × 12 × 3 = 108. Похибка рівнів за номером спроби з випадковою затримкою — до D_n (до 3 840 с). Вплив на KEDA: ⌈240 000 / 1 000⌉ = 240 бажаних реплік → обмеження 12.

### А.7. Операції СУБД на повтор

Виміряно на таблиці 2·10⁶ рядків (250 000 у стані `scheduled`), частковий індекс `(next_attempt_at) WHERE state = 'scheduled'` (5,5 МБ): порожнє опитування `… LIMIT 100 FOR UPDATE SKIP LOCKED` — 0,099 мс (10 064 запитів/с); захоплення пакета 100 рядків (`UPDATE … FROM (SELECT … SKIP LOCKED)`) — 3,27 мс (306 пакетів/с, 33 мкс на рядок); умовне захоплення одного рядка — 0,34 мс на одному з'єднанні (2 941/с), 7 594/с на 8 з'єднаннях.

| Артефакт | А1 | А3 |
|---|---|---|

| Скрипти | `claimDue.lua`, `ackDue.lua` | SQL захоплення для PostgreSQL і MySQL; цикл `findOneAndUpdate` для MongoDB |
| Прикладні компоненти | `DueTaskPoller`, `ScheduleReconciler`, `ScheduleIndexRebuilder` (блокування, епоха) | `DueTaskPoller` |
| Тести | контрактні тести індексу; тести відмов W1, W2; сценарій `FLUSHALL` (E) | контрактні тести захоплення для 3 СУБД |
| Разом | ≈ 8 | ≈ 5 |

Паркування endpoint-а (D3-02) потрібне в обох альтернативах і до підрахунку не входить.

## Додаток В. Виправлена редакція ADR-001 (кандидат на статус Approved)

```markdown
# ADR-001: Механізм планування відкладених спроб доставки

**Статус:** Proposed → Approved після виконання критеріїв розділу «Верифікація»
**Дата:** 2026-11-18
**Пов'язані елементи C4:** L2 — Delivery Worker, Redis, СУБД, брокер; L3 — DueTaskPoller,
ScheduleIndexRebuilder, ScheduleReconciler, EndpointParking, ScheduleIndex, TaskRepository

## Context

Платформа доставляє вебхуки з семантикою at-least-once (SRS-FUN-10). Механізм відкладення
обслуговує два класи завдань:
(а) повтор після тимчасової відмови: затримка random(0, min(cap, base·2^(n−1))), base = 60 с,
    7 повторів (8 спроб з урахуванням першої), максимальна затримка 3 840 с, горизонт —
    7 620 с максимум і 3 810 с у середньому; за Retry-After — до cap = 21 600 с (SRS-FUN-03.4, 03.5);
(б) відкладення без збільшення лічильника спроб: стан Open Circuit Breaker, ліміт частоти
    endpoint-а, переповнення Bulkhead, упорядкована доставка, недоступність провайдера ключів
    (SRS-FUN-02.5, 04.1, 04.4, 05.2, SRS-NFR-REL-14).
Відкладене завдання не повинне займати слоту обробки й блокувати партицію або чергу
(SRS-FUN-04.1, SRS-NFR-REL-02). Джерело істини стану завдання і часу наступної спроби — СУБД;
після втрати даних Redis розклад відновлюється ≤ 60 с (SRS-NFR-REL-10). SRS-DC-06 допускає
індекс у Redis або персистентні retry-топіки. Механізм працює однаково для PostgreSQL, MySQL 8.4,
MongoDB (replica set), Kafka і RabbitMQ (SRS-DC-04, SRS-EXP-01, SRS-NFR-MNT-01).
Навантаження: за ПН-1 частка повторів — 0; у сценарії SRS-NFR-REL-02 — 400 завдань/с
до недоступного endpoint-а; у стаціонарному стані 80% стійких відмов індекс повторів
містить до 1,5·10⁶ записів.

## Decision Drivers

DD-1…DD-9 (таблиця D1-01 звіту рецензування).

## Alternatives

А1. Індекс розкладу в Redis (Sorted Set) + СУБД як джерело істини + звірка.
    Недоліки: неатомарний подвійний запис; Redis переходить у клас компонента шляху доставки
    (noeviction, AOF, ACL); відновлення і звірка; блокування циклу подій Lua-скриптом
    ≈ 5 мкс на елемент; пам'ять O(λ·W), до 270 МБ у стаціонарному стані повної відмови.
А2. Персистентні retry-топіки (Kafka) / черги очікування з TTL черги і DLX (RabbitMQ).
    Похибка 1 с потребує двійкового розкладу на 12 рівнів (15 з урахуванням Retry-After),
    6–7,5 переходів на повтор, 432–540 реплік партицій; дві реалізації для двох брокерів;
    повідомлення, що очікують, входять до lag KEDA; плагін відкладених повідомлень RabbitMQ
    не підтримується і зберігає дані в одній репліці; Kafka не має вбудованої відкладеної
    доставки (KIP-1277 — Under Discussion); стан дублюється в брокері, звірка з СУБД потрібна.
А3. Опитування СУБД (FOR UPDATE SKIP LOCKED).
    Переваги: немає подвійного запису і відновлення; Redis залишається fail-open.
    Недоліки: MongoDB не підтримує SKIP LOCKED (N викликів findOneAndUpdate на пакет,
    конкуренція опитувачів); 3 реалізації захоплення, залежні від СУБД (вплив на SRS-RQ-02);
    сирий SQL поза API Prisma; варіант не входить до SRS-DC-06.
    Додаткове навантаження — ≤ 12 запитів/с (≤ 0,34% базового).
А4. BullMQ: стан завдань у Redis суперечить SRS-NFR-REL-10. Відхилено.
А5. Гібрид А1 з вікном H: пам'ять ≤ λ·H; додатковий стан завдання. Резервний варіант.

## Decision

Обрано А1 з таким протоколом:
P1. reschedule у транзакції спроби (state = scheduled, attempt = n+1, next_attempt_at = t);
    після фіксації — ZADD sched t "{task_id}:{n+1}"; помилка ZADD не скасовує транзакції.
P2. claimDue (Lua, кожна репліка раз на 1 с, N = 200, ≤ 2 мс): перевірка sched:epoch;
    оренда ZADD XX (now + 30 с) замість вилучення.
P3. Публікація в tasks із ключем endpoint_id з підтвердженням брокера; після підтвердження —
    умовний ZREM (ackDue).
P4. Захоплення в СУБД з умовою state = scheduled, attempt = n, next_attempt_at ≤ now;
    0 рядків — підтвердження повідомлення без доставки.
P5. Звірка кожні 60 с одним виконавцем: прострочені на > 5 с завдання scheduled — повторний ZADD;
    прострочені оренди in_flight — повернення в scheduled. Обхід за середовищами клієнтів (SEC-11).
P6. Відновлення за відсутності sched:epoch: потокове читання сторінками по 1 000 рядків,
    конвеєрний ZADD; вивільнення прострочених ≤ 500 завдань/с.
P7. Клас (б): паркування endpoint-а — завдання в стані parked у СУБД, один запис ep:{endpoint_id}
    в індексі; відновлення сторінками з дотриманням лімітів endpoint-а.
Члени індексу містять лише task_id і номер спроби.
Дистрибутив: Valkey 9.x (BSD-3), офіційний Helm-чарт; maxmemory 512 МБ, noeviction, AOF everysec,
ACL-користувачі для API, воркера і Job-а експерименту.

Підстави вибору: DD-3 — одна реалізація логіки планування для 3 СУБД і 2 брокерів, без залежної
від СУБД складової в результатах SRS-RQ-02; DD-4 — довільна затримка до 21 600 с без рівнів;
DD-7 — відповідає SRS-DC-06. Пропускна здатність не є чинником вибору (≤ 2·10³ оп/с).

## Consequences

Позитивні:
- логіка планування не залежить від брокера і СУБД; повторна публікація з ключем endpoint_id;
- планова затримка обчислюється без квантування; похибка запуску ε = δ_poll + δ_pub + δ_q,
  δ_poll ≤ 1 с, ціль ε p95 ≤ 2 с;
- механізм не додає операцій запису в СУБД понад обов'язкові за SRS-NFR-REL-10.
Негативні:
- запис у СУБД і в індекс неатомарний; завдання без запису в індексі повторюється не пізніше
  ніж через 65 с після планового часу (звірка P5);
- Redis переходить у клас компонента шляху доставки: noeviction, AOF, ACL, резервування 1 ГБ пам'яті;
  недоступність Redis затримує повтори, але не втрачає їх;
- пам'ять індексу O(λ·W): до 216–270 МБ у стаціонарному стані масових відмов;
- відновлення індексу: повне читання розкладу з СУБД, вимога ≤ 60 с перевіряється для кожної СУБД;
- Lua-скрипти блокують Redis на ≈ 1 мс за N = 200, спільний ресурс з Token Bucket прийому;
- звірка і відновлення — кросс-середовищні читання з обходом за середовищами клієнтів;
- обсяг реалізації ≈ 8 артефактів; Testcontainers Redis/Valkey у PR; сценарій FLUSHALL у E;
- ліцензійний і операційний ризик дистрибутива Redis знижується вибором Valkey і обмеженим
  набором команд порту ScheduleIndex.

## Верифікація

- PR: контрактні тести ScheduleIndex (Valkey, Redis 8); тести відмов W1, W2 з модельним часом звірки;
  модельний тест паркування (Open → Half-Open → Closed без рециркуляції).
- E: SRS-NFR-REL-01 з видаленням pod-а воркера під час claimDue — інваріант 8.2;
  SRS-NFR-REL-10 — FLUSHALL під навантаженням, schedule_rebuild_duration_seconds ≤ 60 с для кожної СУБД;
  SRS-NFR-REL-02 — parked_endpoints = 1, відсутність зростання lag tasks;
  schedule_dispatch_lag_seconds p95 ≤ 2 с за ПН-1 з 10% відповідей 5xx.
```
