# ADR-001: Механізм планування відкладених спроб доставки

**Статус:** Approved
**Дата:** 2026-11-18
**Автор:** Куруляк Е.
**Пов'язані вимоги:** [SRS-DC-06](../srs.md#srs-dc-06), [SRS-NFR-REL-10](../srs.md#srs-nfr-rel-10), [SRS-FUN-03.4](../srs.md#srs-fun-03-4), [SRS-FUN-03.5](../srs.md#srs-fun-03-5), [SRS-FUN-04.4](../srs.md#srs-fun-04-4), [SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02)
**Пов'язані елементи C4:** [L2 — Delivery Worker, Redis-сумісне сховище, СУБД, брокер](../2_design.md#diagram-level2); [L3 — DueTaskPoller, ScheduleIndexRebuilder + Reconciler, EndpointParking, ScheduleIndex, TaskRepository](../2_design.md#diagram-level3)

## Context

Платформа доставляє вебхуки з семантикою at-least-once ([SRS-FUN-10](../srs.md#srs-fun-10)). Механізм відкладення обслуговує два класи завдань:

- **(а) повтор після тимчасової відмови:** затримка `random(0, min(cap, base·2^(n−1)))`, base = 60 с, 7 повторів (8 спроб), максимальна затримка без `Retry-After` — 3 840 с, з `Retry-After` — до cap = 21 600 с ([SRS-FUN-03.4](../srs.md#srs-fun-03-4), 03.5);
- **(б) відкладення без збільшення лічильника спроб:** Circuit Breaker у стані Open, ліміт частоти, переповнення Bulkhead, упорядкована доставка, недоступність провайдера ключів ([SRS-FUN-02.5](../srs.md#srs-fun-02-5), 04.1, 04.4, 05.2, [SRS-NFR-REL-14](../srs.md#srs-nfr-rel-14)).

Обмеження:

- відкладене завдання не займає слоту обробки і не блокує партицію або чергу ([SRS-FUN-04.1](../srs.md#srs-fun-04-1), [SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02));
- джерело істини стану завдання і часу наступної спроби — СУБД; після втрати даних індексу розклад відновлюється ≤ 60 с ([SRS-NFR-REL-10](../srs.md#srs-nfr-rel-10));
- [SRS-DC-06](../srs.md#srs-dc-06) допускає індекс у Redis або персистентні retry-топіки; Thesis Proposal фіксує Redis як планувальник відкладених спроб;
- механізм працює однаково для PostgreSQL, MySQL 8.4, MongoDB (replica set), Kafka і RabbitMQ, оскільки СУБД і брокер — параметри експерименту ([SRS-DC-04](../srs.md#srs-dc-04), [SRS-EXP-01](../srs.md#srs-exp-01), [SRS-NFR-MNT-01](../srs.md#srs-nfr-mnt-01));
- проєкт виконує один розробник; бюджет прикладного рівня — 2 vCPU, 1 ГБ RAM.

Навантаження: за ПН-1 частка повторів дорівнює 0; у сценарії [SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02) до недоступного endpoint-а надходить 400 завдань/с.

## Decision Drivers

| ID | Чинник | Мірило |
|---|---|---|

| DD-2 | Відновлюваність | розклад відновлюється ≤ 60 с після втрати даних індексу ([REL-10](../srs.md#srs-nfr-rel-10)) |
| DD-3 | Паритет адаптерів | кількість реалізацій механізму для 3 СУБД і 2 брокерів |
| DD-4 | Точність | довільна затримка до 21 600 с; похибка запуску p95 ≤ 2 с |
| DD-5 | Ізоляція | відкладені завдання не рециркулюють через брокер ([REL-02](../srs.md#srs-nfr-rel-02)) |
| DD-6 | Ресурси (FinOps) | додаткові операції СУБД, брокера і пам'ять у межах бюджету 5.0 |
| DD-7 | Відповідність SRS | без зміни [SRS-DC-06](../srs.md#srs-dc-06) і Thesis Proposal |
| DD-8 | Обсяг реалізації | кількість артефактів для одного розробника |

## Alternatives

**А1. Індекс розкладу в Redis-сумісному сховищі (Sorted Set) + СУБД як джерело істини + звірка.**
Переваги: одна реалізація індексу для всіх СУБД і брокерів; довільна затримка без квантування; повторна публікація в `tasks` з ключем `endpoint_id` повертає завдання до репліки-власника endpoint-а.
Недоліки: запис у СУБД і в індекс неатомарний; сховище переходить із класу fail-open у компонент шляху доставки; потрібні звірка і відновлення індексу; пам'ять зростає як O(λ·W).

**А2. Персистентні retry-топіки (Kafka) або черги очікування з TTL і dead-letter exchange (RabbitMQ).**
Kafka не має вбудованої відкладеної доставки: KIP-1277 має статус Under Discussion і розрахований на затримки до 15 хв. Плагін відкладених повідомлень RabbitMQ не підтримується з квітня 2026 р., зберігає дані в одній репліці Mnesia, а Mnesia вилучено з RabbitMQ 4.3. TTL окремого повідомлення спрацьовує лише на голові черги, тому випадкова затримка full jitter потребує двійкового розкладу на 12–15 рівнів: 6–7,5 переходів на один повтор, 432–540 реплік партицій Kafka. Реалізації для Kafka і RabbitMQ різні. Повідомлення, що очікують, входять до lag групи споживачів і спотворюють масштабування KEDA. Стан дублюється в брокері, тож звірка з СУБД потрібна і тут.

**А3. Опитування таблиці завдань у СУБД (`FOR UPDATE SKIP LOCKED`).**
Переваги: немає подвійного запису і відновлення індексу; Redis залишається fail-open; додаткове навантаження — ≤ 12 запитів/с, тобто ≤ 0,34% базового навантаження СУБД.
Недоліки: MongoDB не має аналога `SKIP LOCKED` (пакет із N завдань — N викликів `findOneAndUpdate` з конкуренцією опитувачів); три реалізації захоплення, залежні від СУБД, які потрапляють у результати порівняння СУБД ([SRS-RQ-02](../srs.md#srs-rq-02)); `SKIP LOCKED` недоступний через API Prisma і вимагає сирого SQL; варіант не передбачений [SRS-DC-06](../srs.md#srs-dc-06).

**Відхилені без детального аналізу:** BullMQ — робить Redis джерелом істини, що суперечить [REL-10](../srs.md#srs-nfr-rel-10); pg-boss, graphile-worker — лише PostgreSQL, суперечать [DC-04](../srs.md#srs-dc-04); таймерне колесо в пам'яті репліки — найбільший обсяг реалізації через перенесення стану під час ребалансування.

| Чинник | А1 | А2 | А3 |
|---|---|---|---|
| DD-1 Збереженість | так, за звірки P5 | так; звірка з СУБД потрібна | так, похідного стану немає |
| DD-2 Відновлюваність | відновлення індексу (P6) | стан дублюється в брокері | не потрібне |

| DD-5 Ізоляція | за паркування endpoint-а | за паркування; lag KEDA спотворюється | за паркування |

## Decision

Обрано **А1** з протоколом узгодження P1–P7.

| Крок | Дія |
|---|---|
| P1 | `reschedule` в одній транзакції із записом спроби: `state = 'scheduled'`, `attempt = n + 1`, `next_attempt_at = t`. Після фіксації — `ZADD sched t "{task_id}:{n+1}"`; помилка `ZADD` не скасовує транзакції і збільшує `schedule_index_errors_total`. |
| P2 | `claimDue` (Lua, кожна репліка раз на 1 с, N = 200): перевірка ключа епохи `sched:epoch`; оренда `ZADD XX (now + 30 с)` замість вилучення. |
| P3 | Публікація в `tasks` із ключем `endpoint_id` з підтвердженням брокера (`acks=all` / publisher confirm); після підтвердження — умовний `ZREM` (`ackDue`). |
| P4 | Захоплення в СУБД з умовою `state = 'scheduled' AND attempt = n AND next_attempt_at <= now()`; 0 змінених рядків — підтвердження повідомлення без доставки (захист від дублікатів і застарілих записів індексу). |
| P5 | Звірка кожні 60 с одним виконавцем (`SET … NX PX`): завдання `scheduled`, прострочені понад 5 с, — повторний `ZADD`; прострочені оренди `in_flight` — повернення в `scheduled`. Обхід за середовищами клієнтів. |
| P6 | Відновлення за відсутності `sched:epoch`: потокове читання розкладу сторінками по 1 000 рядків, конвеєрний `ZADD`. |
| P7 | Клас (б) — паркування endpoint-а: завдання в стані `parked` у СУБД, один запис `ep:{endpoint_id}` в індексі зі score = час переходу до Half-Open; відновлення сторінками з дотриманням лімітів endpoint-а і порядку для `ordered = true`. |

Записи індексу містять лише `task_id` і номер спроби, без payload.

Конфігурація сховища: дистрибутив **Valkey 9.x** (BSD-3-Clause), Redis-сумісний; офіційний Helm-чарт Valkey з фіксованими версіями чарта й образу; `maxmemory` 512 МБ, `maxmemory-policy noeviction`, AOF `appendfsync everysec`, окремі ACL-користувачі для API і воркера. Порт `ScheduleIndex` використовує лише команди, наявні в Redis 7.2 і Valkey (`ZADD` з `XX`/`GT`, `ZRANGE … BYSCORE … LIMIT`, `ZREM`, `EVALSHA`, `SET … NX PX`), тому дистрибутив замінний.

Підстави вибору:

- **DD-3:** одна реалізація планування для 3 СУБД і 2 брокерів; результати порівняння СУБД ([SRS-RQ-02](../srs.md#srs-rq-02)) не містять складової, залежної від механізму захоплення;
- **DD-4:** довільна затримка до 21 600 с без рівнів і квантування розподілу full jitter;
- **DD-7:** відповідає [SRS-DC-06](../srs.md#srs-dc-06) і затвердженому Thesis Proposal.

Пропускна здатність не є чинником вибору: усі альтернативи обслуговують ≤ 2·10³ операцій/с. За DD-1, DD-2 і DD-8 перевагу має А3; ціну вибору А1 відображено в негативних наслідках.

## Consequences

**Позитивні:**

- логіка планування не залежить від СУБД і брокера, контрактні тести порту `ScheduleIndex` однакові для всіх конфігурацій ([SRS-NFR-MNT-01](../srs.md#srs-nfr-mnt-01));
- планова затримка обчислюється без квантування; похибка запуску ε = δ_poll + δ_pub + δ_q, δ_poll ≤ 1 с, ціль ε p95 ≤ 2 с;
- паркування обмежує індекс у сценарії [SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02) до ≤ 1 000 записів (≈ 142 КБ) і усуває рециркуляцію 400 завдань/с через брокер;
- механізм не додає записів у СУБД понад обов'язкові за [SRS-NFR-REL-10](../srs.md#srs-nfr-rel-10).

**Негативні:**

- запис у СУБД і в індекс неатомарний: завдання без запису в індексі повторюється не пізніше ніж через 65 с після планового часу (звірка P5), що збільшує хвіст затримки повтору;
- Redis-сумісне сховище переходить у клас компонента шляху доставки: `noeviction`, AOF, постійний том, ACL; його недоступність затримує повтори до відновлення і звірки, але не втрачає їх;
- пам'ять індексу O(λ·W): до 216–270 МБ у стаціонарному стані масових відмов без розмикання Circuit Breaker; за довгих `Retry-After` — потенційно більше, що є умовою перегляду рішення;
- відновлення індексу читає весь розклад із СУБД; вимога ≤ 60 с перевіряється окремо для кожної СУБД;
- Lua-скрипт `claimDue` блокує сховище ≈ 1 мс за N = 200; сховище спільне з Token Bucket прийому, тому N обмежено;
- звірка і відновлення читають завдання всіх середовищ клієнтів; обхід виконується за середовищами з фільтром за ідентифікатором ([SRS-NFR-SEC-11](../srs.md#srs-nfr-sec-11));
- обсяг реалізації ≈ 8 артефактів замість ≈ 5 для А3; CI додає контейнер Valkey у Testcontainers і сценарій `FLUSHALL` в експериментальній кампанії;
- FinOps: резервування до 1 ГБ пам'яті для сховища з AOF (запас на перезапис AOF) на інфраструктурному рівні;
- ліцензійний ризик дистрибутива: Redis 7.4+ поширюється за RSALv2/SSPL, Redis 8 додав AGPLv3; ризик знижено вибором Valkey і обмеженим набором команд.

## Верифікація

- **PR:** контрактні тести `ScheduleIndex` (Valkey); тести відмов між P1 і `ZADD` та між P2 і P3 з модельним часом звірки; модельний тест паркування Open → Half-Open → Closed без рециркуляції.
- **E:** SRS-NFR-REL-01 з видаленням pod-а воркера під час `claimDue` — інваріант 8.2; [SRS-NFR-REL-10](../srs.md#srs-nfr-rel-10) — `FLUSHALL` під навантаженням, `schedule_rebuild_duration_seconds` ≤ 60 с для кожної СУБД; [SRS-NFR-REL-02](../srs.md#srs-nfr-rel-02) — `parked_endpoints` = 1 і відсутність зростання lag `tasks`.
- **Метрики, що додаються до каталогу 7.2:** `schedule_index_size`, `schedule_index_errors_total{op}`, `schedule_reconciled_total`, `schedule_rebuild_duration_seconds`, `schedule_dispatch_lag_seconds`, `parked_endpoints`.

## Умови перегляду

Рішення переглядається, якщо:

- `schedule_reconciled_total` > 0,1% повторів у прогонах без ін'єкції відмов сховища;
- пам'ять індексу перевищує 70% `maxmemory` у будь-якому сценарії кампанії (тоді — гібрид із вікном H, у якому індекс містить лише завдання з `next_attempt_at ≤ now + H`);
- Kafka або RabbitMQ отримують стабільну вбудовану відкладену доставку з реплікацією і затримками до 6 год;
- з домену експерименту вилучається MongoDB (тоді А3 стає простішою).
